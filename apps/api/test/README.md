# Тесты API

| Набор | Команда | Что нужно |
|---|---|---|
| Юнит (`test/*.test.ts`) | `pnpm --filter @teletau/api test` | ничего: Postgres и Valkey подменены |
| Интеграционные (`test/integration/`) | `pnpm --filter @teletau/api test:integration` | Docker-стек проекта (`pnpm dev` или `docker compose up -d --wait`). Миграции dev-базы не нужны: у тестов своя база (ниже) |
| Сквозные в браузере (`e2e/`, корень репозитория) | `pnpm e2e` | Docker. Сам применяет миграции, загружает справочник, собирает и запускает api, web и console на портах из `.env`, после прогона их останавливает |

**Своя база (M1-50).** Интеграционные тесты не пишут в dev-базу из корневого `.env`: там их заявки учителей накапливались в очереди модератора и ломали e2e. Из `DATABASE_URL` и `VALKEY_URL` корневого `.env` (или значений по умолчанию) `vitest.config.ts` строит адреса на тех же серверах: база `<имя>_it` (`teletau_it`) и следующий номер базы Valkey (`/1`). Построение адресов — `test/integration/it-env.ts`. Перед каждым прогоном `test/integration/global-setup.ts`:
1. пересоздаёт базу (`DROP DATABASE … WITH (FORCE)`, `CREATE DATABASE`). Удалить он может только базу с суффиксом `_it`;
2. применяет миграции из `drizzle/` программным мигратором drizzle — тем же журналом, что у `drizzle-kit migrate`;
3. загружает справочник районов и школ с демо-школами;
4. очищает базу Valkey тестов.

После прогона база остаётся, её можно посмотреть: `docker compose exec postgres psql -U teletau -d teletau_it`. Dev-база и ключи dev в Valkey не меняются. Тесты, которые сами поднимают приложение или TCP-прокси (`resilience.test.ts`), берут адреса из того же окружения. Два прогона одновременно на одной машине мешают друг другу: второй пересоздаёт базу первого.

Файлы внутри прогона идут по очереди, потому что база и Valkey у них общие. У каждого файла свои адреса e-mail и IP, поэтому лимиты частоты и аудит одного файла не мешают другому. Демо-режим входа (`AUTH_DEMO_OTP=0000`) и демо-сотрудников (`AUTH_DEMO_STAFF=1`) тесты включают сами.

## Как вручную повторить проверку повторного использования refresh-токена (демо §6.2)

Нужен запущенный API (`pnpm dev`) в демо-режиме. Команды печатают токены в терминал: это демо-аккаунт, но историю оболочки лучше потом очистить.

```sh
API=http://localhost:4000/api/v1
DEV=$(node -e 'console.log(crypto.randomUUID())')
json() { node -e 'let s="";process.stdin.on("data",d=>s+=d).on("end",()=>console.log(JSON.parse(s)'"$1"'))'; }

# 1. Войти взрослым: e-mail и демо-код 0000
CH=$(curl -s $API/auth/otp/request -H 'content-type: application/json' -d '{"email":"reuse.demo@school.example.org"}' | json .challengeId)
R0=$(curl -s $API/auth/otp/verify -H 'content-type: application/json' \
  -d "{\"challengeId\":\"$CH\",\"code\":\"0000\",\"device\":{\"installId\":\"$DEV\",\"platform\":\"web\"}}" | json .refreshToken)

# 2. Обновить сессию дважды: R0 → R1 → R2. Законный клиент уже пользуется преемником R1, поэтому льготного окна
#    для потерянного ответа (60 с, ADR 0015 §2) у R0 больше нет
S1=$(curl -s $API/auth/refresh -H 'content-type: application/json' -d "{\"refreshToken\":\"$R0\",\"deviceInstallId\":\"$DEV\"}")
R1=$(echo "$S1" | json .refreshToken)
S2=$(curl -s $API/auth/refresh -H 'content-type: application/json' -d "{\"refreshToken\":\"$R1\",\"deviceInstallId\":\"$DEV\"}")
R2=$(echo "$S2" | json .refreshToken); A2=$(echo "$S2" | json .accessToken)

# 3. Предъявить старый R0 повторно → 401 {"code":"refresh_reused"}: отозвано всё семейство
curl -s $API/auth/refresh -H 'content-type: application/json' -d "{\"refreshToken\":\"$R0\",\"deviceInstallId\":\"$DEV\"}"

# 4. Новый R2 тоже не работает (refresh_reused), access-токен A2 отвергается сразу (стоп-лист): 401 session_revoked
curl -s $API/auth/refresh -H 'content-type: application/json' -d "{\"refreshToken\":\"$R2\",\"deviceInstallId\":\"$DEV\"}"
curl -s $API/me -H "authorization: Bearer $A2"

# 5. Запись в журнале аудита: в консоли («Журнал аудита», фильтр session.refresh_reuse_detected) или в базе
docker compose exec -T postgres psql -U teletau -d teletau -c \
  "SELECT created_at, action, actor_account_id, target_id FROM audit_log WHERE action = 'session.refresh_reuse_detected' ORDER BY created_at DESC LIMIT 3"
```

Автоматическая версия — тест `§6.2: reusing an old refresh token…` в `integration/m1-flow.test.ts`. Если повторить R0 сразу после шага с R1 (без R2), сработает льготное окно потерянного ответа: новая пара без отзыва семейства (`integration/m1-round2.test.ts`).
