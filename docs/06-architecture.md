# 06. Архитектура системы

## 1. Архитектурные драйверы

| Драйвер | Следствие для архитектуры |
|---|---|
| 4+ клиента (веб, iOS, Android, бот/мини-приложение) и внешний API | **Contract-first**: OpenAPI — единственный источник правды, клиенты генерируются |
| Нативные iOS/Android без кроссплатформенных фреймворков | Общая логика (проверка ответов, FSRS, нормализация, орнамент) дублируется на Swift/Kotlin/TS → **общие тест-векторы** гарантируют одинаковое поведение |
| Сельские школы со слабой связью | **Offline-first** клиенты, синхронизация журналом событий |
| Пиковая нагрузка в учебное время, «урок-битвы» в реальном времени | Горизонтально масштабируемый stateless API, Redis для рейтингов и pub/sub, WebSocket-шлюз |
| Качество корпуса и аудит решений | **Event sourcing** голосов, пересчитываемое состояние |
| Дети — основные пользователи | Минимизация данных (privacy by design), хранение в РФ, разделение контуров ПДн и аналитики |
| Небольшая команда + разработка с AI-агентами | **Модульный монолит** вместо микросервисов, единый язык (TypeScript) для сервера, веба и бота, жёсткие границы модулей |
| Замедление Telegram в РФ | **Канально-независимое ядро бота**; бот — дополнительный канал; Mini App = веб, открывается и в браузере |
| AI-провайдер может меняться/дорожать | **AI-шлюз** с бюджетами, кешем, оценками качества |

### Модули API и их ответственность

| Модуль | Ответственность | Владеет таблицами |
|---|---|---|
| `identity` (M1) | Аккаунты, вход (QR-карточки, коды классов, e-mail + одноразовый код, TOTP сотрудников; OAuth-провайдеры — после M1), сессии, устройства, роли, ники, контроль доступа (`x-access`), демо-сотрудники | `accounts`, `credentials`, `sessions`, `devices`, `pii.adult_profiles` |
| `consent` (M1) | Согласия (версии документов и их тексты, кто/когда/какое), бумажное согласие на место ученика, отзыв (блокирует вход по карточке) | `consents`, `legal_documents` |
| `org` (M1) | Районы, школы (справочник РБ, импорт `org:import`), классы, места и QR-карточки, код класса и заявки на вход, членство, учебные годы, PDF карточек | `districts`, `schools`, `classes`, `class_seats`, `seat_cards`, `memberships`, `join_requests` |
| `content` (M2) | Курс из YAML (`content:import`, версия и хеш), юниты, узлы тропы, упражнения с ключами ответов (только на сервере); позже — медиа, релизы, офлайн-пакеты | `content_versions`, `units`, `lessons`, `exercises`; позже `media`, `content_releases` |
| `learning` (M2) | Тропа (`GET /course`), забеги уроков с планом показа, проверка ответа `matchAnswer` (`@teletau/bashkir-text`), голос дуэли урока → `ConsensusService.recordVote`, итог → `ProgressService`; позже — Elo, миссия дня | `lesson_runs`, `attempts`; позже `daily_missions`, `skill_ratings` |
| `srs` | FSRS-состояния, журнал повторений | `srs_cards`, `review_log` |
| `progress` (M2) | Мёд (урок; голос — `pending` → `final`), серия по суткам Уфы из дней занятий, счётчики, прохождение узлов, прогресс класса для учителя; позже — достижения, орнамент | `xp_ledger`, `activity_days`, `streaks`, `lesson_progress`, `progress_counters`; позже `achievements` |
| `competition` (M2) | Недельная лига медоносов (5 тиров, группы ≤ 20, ленивое закрытие недели), квест и участие класса; позже — индексы, сезоны, урок-битвы | `league_groups`, `league_members`, `class_week_activity`; позже `hive_index`, `seasons`, `battles` |
| `corpus` (M2) | Исходники и варианты дуэлей из открытых источников (`corpus:import`, `origin = import`); позже — метки, заказы | `source_items`, `variants`; позже `orders` |
| `consensus` (M2: дуэль v0, ADR 0019) | Журнал голосов с группой (дети / учителя / взрослые), выбор пар без своих голосов, состояние по `duel-v0` из журнала, голоса по группам; позже (M4) — надёжность, маршрутизация, эскалации, релизы | `judgments` (только вставка), `item_state`; позже `reliability`, `gold_items`, `releases` |
| `moderation` | Жалобы, фильтры, санкции, проверка учителей (M1) | `teacher_verifications` (M1), `reports`, `sanctions` |
| `notifications` | Пуши, бот, e-mail, тихие часы, частотные лимиты | `notification_prefs`, `outbox_notifications` |
| `partners` | Организации-партнёры, ключи, квоты, вебхуки | `partners`, `api_keys`, `webhooks` |
| `public-api` | Внешний REST `/public/v1` (только чтение корпуса + заказы) | — (читает проекции) |
| `realtime` | WebSocket-комнаты урок-битв, живые обновления рейтинга | — (Redis) |
| `analytics-ingest` | Приём клиентских событий, обезличивание, отправка в ClickHouse | — |
| `admin` | Фичефлаги, справочники, аудит-лог (M1: запись в транзакции модуля, чтение — `GET /admin/audit-log`) | `audit_log` (M1), `feature_flags` |

**Правило границ:** модуль обращается к другому только через его публичный сервис-интерфейс или доменные события; прямые запросы к чужим таблицам запрещены и проверяются в CI скриптом `apps/api/scripts/boundaries.mjs` (импорт чужого модуля — только через его `index.ts`; таблицы модуля — только в его `*.schema.ts` и не реэкспортируются из `index.ts`; `src/{infra,common,db,config}` не зависят от модулей; нет циклов; dependency-cruiser не работает на нечётных версиях Node). Сырые SQL-запросы к чужим таблицам статически не ловятся — защита в рантайме (отдельная схема и роль Postgres на модуль) предложена в ADR 0014. Это позволит выделить модуль в сервис, если понадобится (первые кандидаты: `realtime`, `consensus`).

## 6. Ключевые сквозные решения

### 6.1. Contract-first и генерация клиентов
`packages/contracts/openapi.yaml` → (а) TS-типы (`openapi-typescript`) для API и веба, а `openapi.json` — для проверки запросов в API (ajv, правило `x-access`); (б) Swift-клиент через `swift-openapi-generator`; (в) Kotlin-модели и клиент через `openapi-generator` (kotlinx.serialization + Ktor). CI падает, если спецификация изменена без перегенерации клиентов или есть ломающее изменение без новой версии.

### 6.2. Общие тест-векторы вместо общей кодовой базы
Логика, которая должна работать офлайн на телефоне и одинаково на сервере, реализуется трижды (TS, Swift, Kotlin) и проверяется одними JSON-векторами:

| Набор | Пример вектора |
|---|---|
| `bashkir-text/normalize` | `{"in": "Kыҙыk", "out": "кыҙык", "notes": "латиница K → кириллица"}` |
| `bashkir-text/match` | ответ, принятые варианты → `{verdict: "almost", hint: {pos: 0, expected: "ҡ"}}` |
| `fsrs` | журнал повторений → ожидаемые stability/difficulty/due |
| `xp` | события сессии → начисленные баллы |
| `ornament` | seed + юниты → JSON фигур (и эталонный PNG для снапшотов) |
| `consensus` | журнал голосов → состояние исходника |

Так мы получаем выгоды общего кода без кроссплатформенного фреймворка — и сохраняем полностью нативные приложения.

### 6.3. Offline-first синхронизация
- Клиент хранит контент (офлайн-пакеты юнитов, подписанные и версионированные), состояния FSRS и **журнал событий** (ответы, завершения уроков, голоса) с идентификаторами UUIDv7, сгенерированными на клиенте.
- `POST /sync/push` — пачка событий; сервер идемпотентен по идентификатору события.
- `GET /sync/pull?cursor=…` — изменения с сервера (новые миссии, решения консенсуса, бал, лиги) по курсору.
- **Сервер — источник истины для баллов и рейтингов**: он пересчитывает начисления из событий (с проверкой ответов там, где ключ известен) — офлайн-клиент лишь показывает предварительный результат. Это закрывает накрутку через подделку клиента.
- Голоса в корпус, сделанные офлайн, учитываются с пометкой времени; задания на корпус выдаются в офлайн-пакет с запасом и истекают через 72 ч.
- Конфликтов «последний победил» нет: прогресс — только добавление событий; настройки профиля — по версии поля.

### 6.4. Доменные события и outbox
Модули публикуют события (`LessonCompleted`, `JudgmentRecorded`, `ItemAccepted`, `StreakExtended`, `ClassQuestCompleted`…) в таблицу `outbox` в той же транзакции, что и изменения; ретранслятор кладёт их в BullMQ. Потребители: уведомления, рейтинги, аналитика, вебхуки партнёров, ml-worker. Гарантия «как минимум один раз» + идемпотентные обработчики.

### 6.5. Рейтинги и лиги
- Лидерборды лиг и классов — Redis sorted sets (`ZINCRBY` по событию начисления), снимок в PostgreSQL каждые 5 минут и при закрытии недели.
- «Индекс улья» — пакетный пересчёт раз в час (и итоговый в конце недели) в воркере; публикуется только после антифрод-проверки.

### 6.6. Реальное время (урок-битва)
WebSocket-шлюз в модуле `realtime`: комнаты по коду битвы, состояние раунда в Redis, горизонтальное масштабирование через Redis pub/sub-адаптер. Протокол — JSON-сообщения со схемами в `contracts/`. Учитель — ведущий, сервер — арбитр времени (клиентские часы не доверены).

### 6.7. Поиск по словарю
PostgreSQL: нормализованный текст + `pg_trgm` (нечёткий поиск с опечатками и свёрткой букв), полнотекст по русской стороне, `pgvector` (эмбеддинги) для «похожих по смыслу». Сортировка выдачи по башкирскому алфавиту (А Б В Г Ғ Д Ҙ Е Ё Ж З И Й К Ҡ Л М Н Ң О Ө П Р С Ҫ Т У Ү Ф Х Һ Ц Ч Ш Щ Ъ Ы Ь Э Ә Ю Я). В CLDR нет башкирской сортировки: `Intl.Collator("ba")` откатывается к корневой и ставит Ә после А, а не после Э. Остальные буквы корневая сортировка ставит верно. Решение:
- **PostgreSQL 16+:** `CREATE COLLATION ba_tailored (provider = icu, locale = 'ru', rules = '&Э < ә <<< Ә')`;
- **Android:** `android.icu.text.RuleBasedCollator` с тем же правилом;
- **iOS и веб** (правила там не поддерживаются): собственный ключ сортировки из `bashkir-text`;
- всё проверяется тест-векторами сортировки.

### 6.8. Политика таймаутов внешних вызовов (M0-R2-02, M0-R3-02/03/05)

Каждый сетевой вызов наружу ограничен по времени. Иначе соединение, «умершее» без RST (failover управляемой БД с переездом узла, падение ВМ, разрыв сети между зонами), висит до таймаута повторной передачи TCP в ОС — в Linux около 15 минут. Всё это время оно держит клиента пула, а readiness-проба выводит под из балансировки.

| Вызов | Таймауты (по умолчанию, переопределяются переменными окружения) | Что происходит при срабатывании |
|---|---|---|
| Postgres (API) | подключение 2 с; `query_timeout` 5 с (`DB_QUERY_TIMEOUT_MS`); серверный `statement_timeout` 4 с (`DB_STATEMENT_TIMEOUT_MS`, всегда меньше клиентского — проверяется при старте); TCP keep-alive | Запрос завершается ошибкой, клиент возвращается в пул с ошибкой и уничтожается; следующий запрос получает новое соединение |
| Postgres, health-проба | собственный `query_timeout` = `HEALTH_TIMEOUT_MS` (1 с) | Проба отвечает `down`, причина пишется в лог (`health/postgres: …`, не чаще раза в 30 с на код ошибки), мёртвый клиент вычищается — после восстановления сети health возвращается к 200 за секунды |
| Valkey (API) | подключение 2 с; `commandTimeout` 2 с (`VALKEY_COMMAND_TIMEOUT_MS`); `socketTimeout` 3 с (`VALKEY_SOCKET_TIMEOUT_MS`); задержка переподключения `min(n × 100, 1000)` мс | Команда завершается ошибкой; сокет без данных при ожидающих командах уничтожается, клиент переподключается. Худший случай после восстановления сети — `socketTimeout` + 1 с + рукопожатие ≈ 4 с (с задержкой ioredis по умолчанию — до 2 с — выходило до 6,3 с) |
| Valkey (BullMQ, workers) | только `socketTimeout` 15 с (`VALKEY_WORKER_SOCKET_TIMEOUT_MS`, не меньше 12 с) | `commandTimeout` не используется: он оборвал бы штатные блокирующие команды BullMQ. Окна блокировки: `drainDelay` 5 с без отложенных задач и `maximumBlockTimeout` 10 с при отложенных (напоминания, уведомления) — таймаут сокета больше обоих с запасом |
| GigaChat (ai-gateway, с M5) | таймаут запроса, повтор с backoff, предохранитель — `docs/04-ai-gigachat.md` §4 | Деградация до шаблонного ответа |
| BFF веба и консоли → API (`/api/session/*`, `@teletau/session/server`) | 10 с (`BFF_API_TIMEOUT_MS`), `AbortSignal.timeout`; меньше таймаута браузера, чтобы браузер успел получить ответ | Браузеру — 503 `api_unavailable` (Problem Details); клиент показывает «Нет связи», уже открытая сессия не теряется |
| Браузер → API и браузер → BFF (`@teletau/session/api`, `client`) | 15 с на запрос, 60 с на скачивание PDF карточек | `TimeoutError` → состояние «Нет связи» с повтором; опрос страницы класса продолжается со следующего шага, а не висит |
| Страница юридического документа (сервер Next.js → API) | 10 с | «Документ временно недоступен» с кнопкой повтора |

Проверяется интеграционными тестами `apps/api/test/integration/resilience.test.ts` с TCP-прокси в режиме «чёрная дыра»:
- после разрыва длиной 1,5 с (Postgres, Valkey) и 30 с (Valkey) health возвращается к 200 не дольше чем за 5 с, а во время разрыва отвечает 503 не дольше `HEALTH_TIMEOUT_MS` + 0,5 с;
- обычный запрос через пул API во время разрыва завершается ошибкой не позже `DB_QUERY_TIMEOUT_MS` + 1 с, после восстановления сети новый запрос проходит сразу. Без `query_timeout` такие запросы висят, пул исчерпывается, и после восстановления сети новые запросы получают «timeout exceeded when trying to connect» — тест это ловит (проверено мутацией).

Health-проба Postgres использует собственный короткий таймаут, поэтому сама по себе таймаут пула не проверяет — для этого нужен второй сценарий.

### 6.9. Доступ, сессии и аудит (реализовано в M1)

**Модули M1 и направление зависимостей.** В API работают `identity`, `org`, `consent`, `moderation`, `admin` (и `health` из M0). Граф импортов ацикличен: identity → moderation → org → consent → admin. Обратные потребности объявлены портами в `apps/api/src/common/ports.ts`:
- `ACCOUNTS_PORT` реализует `identity` (детский аккаунт без ПДн, ники, ПДн взрослых, роль `teacher`, отзыв сессий);
- `CLASS_ACCESS_PORT` — `org` (место класса для бумажного согласия, «учитель класса»);
- `TEACHER_SCHOOL_PORT` — `moderation` (школа из одобренной заявки для создания класса).

Модуль не читает чужие таблицы — только сервисы и порты (ADR 0014, `boundaries.mjs`).

**Путь запроса.**

| Шаг | Где | Что происходит |
|---|---|---|
| 1 | Fastify `trustProxy` (`TRUST_PROXY`) | `request.ip` — IP клиента. `X-Forwarded-For` учитывается только от доверенных адресов: в dev — `loopback` (BFF Next.js на этом же компьютере), в проде — подсети балансировщика и BFF |
| 2 | хук `onRequest` (`identity/access-control.ts`) | Access-токен JWT ES256 → принципал; семейство сессии проверяется по стоп-листу Valkey; роль сверяется с `x-access` операции из контракта (`@teletau/contracts/openapi.json`). Аноним — 401, чужая роль — 403, ещё до разбора тела. Valkey недоступен — 503 для закрытых операций |
| 3 | хук `preValidation` (`bootstrap.ts`, M1-40) | Управляющие символы (U+0000–U+001F, U+007F–U+009F) в теле, query, пути и заголовках-параметрах операции — 422 с указателем, ещё до схемы и обработчика. NUL не доходит до Postgres, а запрос ничего не успевает израсходовать (например, код из письма) |
| 4 | ajv по схемам контракта | 422 с указателями полей, лишние поля не вырезаются |
| 5 | сервис модуля | Политика ресурса (ADR 0017): `class-teacher`, `class-member`, `self`, `consent-owner`, `poll-token`. Чужой класс — 403, чужая заявка по `X-Poll-Token` — 404 |
| 6 | транзакция модуля | Изменение и строка `audit_log` (через публичный `AuditService` модуля `admin`) — в одной транзакции |

**Сессии в вебе и консоли (ADR 0015 §3).** Вход, обновление и выход идут через BFF — обработчик Next.js `/api/session/[action]` (`packages/session/src/server.ts`, пакет `@teletau/session`, общий для веба и консоли). Refresh-токен и идентификатор установки живут только в httpOnly-cookie на origin приложения. Браузер держит access-токен в памяти вкладки и сам вызывает API (CORS: `PUBLIC_WEB_URL`, `PUBLIC_CONSOLE_URL`). Обновление токена — одно на все вкладки (`navigator.locks`); запросы во время обновления ждут новый токен. BFF передаёт в API IP браузера (`X-Forwarded-For`) и возвращает браузеру `Retry-After` при 429. Присланный клиентом `X-Forwarded-For` BFF не пересылает (M1-05): IP — адрес сокета запроса к Next.js (его кладёт в служебный заголовок HTTP-сервер процесса, `instrumentation.ts` → `@teletau/session/peer`), а если перед Next.js стоит свой балансировщик (`BFF_TRUST_PROXY`) — адрес, который дописал он (самый правый недоверенный в цепочке).

**Заголовки безопасности веба и консоли (M1-11).** `proxy.ts` (Next 16) на каждый запрос создаёт nonce и ставит CSP: `script-src 'self' 'nonce-…' 'strict-dynamic'`, `style-src 'self' 'nonce-…'`, `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`, `connect-src 'self' <API>`; `unsafe-inline` нет ни для скриптов, ни для стилей (атрибутов `style` в разметке нет — проверяет `scripts/check-hardcoded-tokens.mjs`). Ещё — `Permissions-Policy` (камера — только вебу, для сканера карточки), `Referrer-Policy: no-referrer`, `X-Content-Type-Options`, `X-Frame-Options`, HSTS в production. Nonce Next.js проставляет своим скриптам сам, поэтому все страницы рендерятся динамически (`connection()` в корневом layout).

**Аудит.** `audit_log` — только вставка (триггеры и роль `teletau_app`, миграция `0002_m1_guards`). Действия M1:
- карточки и коды: `card.issued`, `card.reissued`, `class.join_code_issued`, `class.join_code_closed`;
- заявки на вход: `join_request.approved`, `join_request.rejected`;
- заявки учителей: `teacher_verification.submitted`, `.approved`, `.rejected`;
- согласия: `consent.given`, `consent.revoked`;
- безопасность: `session.refresh_reuse_detected` (один раз на семейство), `session.device_mismatch`, `staff.login`, `staff.login_failed`, `staff.locked`.

В `metadata` нет ПДн и секретов, вместо IP — `ip_hash`. Читают журнал модератор и администратор: консоль, «Журнал аудита».

**Надёжность при гонках и сбоях (доработка по гейту M1, раунды 1–3).**
- Лимиты частоты атомарны: каждая проверка — один Lua-скрипт в Valkey (`infra/rate-limiter.ts`). Есть два вида лимитов:
  - `consume` считает каждое событие (запросы кода, опросы, обновления сессии);
  - `reserve` считает только неудачи (неверный QR, неверный код класса, неверный `X-Poll-Token`).

  У резерва два счётчика (ADR 0016, уточнения раунда 2): F — зафиксированные неудачи в окне, P — попытки «в работе» (sorted set, у каждой попытки срок жизни 10 с). Слот выдаётся, если F + P < max. По итогу вызывающий явно вызывает `fail()` (неудача уходит в F) или `release()` (всё остальное, в том числе исключение посередине). Поэтому за окно проверяется не больше `max` неверных попыток при любой параллельности, а верные попытки слот неудачи не занимают. Если отказ только из-за P, сервер повторяет резерв с шагом 10–100 мс до 2 с, затем отвечает 429 с `Retry-After: 1`. Если F ≥ max — 429 с остатком окна, в том числе для верной попытки.
- `Idempotency-Key`: маркер «в работе» (`SET NX`, 60 с) ставится до выполнения, второй параллельный запрос получает 409 `request_in_progress` с `Retry-After`. Ключ привязан к хешу тела: другое тело — 422 `idempotency_key_reused`. Упавший запрос ключ освобождает (`infra/idempotency.ts`).
- Отзыв сессий сначала фиксируется в Postgres, затем обновляется стоп-лист Valkey. Сбой Valkey даёт 503, но отзыв не откатывается (ADR 0015).
- Непредвиденная ошибка — Problem 500. В лог пишутся маршрут, SQLSTATE, имена ограничения и таблицы и операция; текст ошибки БД и её параметры не пишутся никогда (`common/errors.ts`).

**Вход на место (ADR 0016 §5 и уточнения раунда 2).** Можно ли войти на место, решает одна проверка — `ClassesService.admitSeat` (модуль org): карточка действует (при входе по QR), класс не в архиве, согласие места не отозвано. Её вызывают все пути входа в транзакции выдачи сессии: вход по QR и выдача сессии при опросе заявки кода класса, первая и повторная. Отказ — тот же Problem, что у QR: 403 `class_archived` или `consent_revoked`.
- **Блокировка места.** `admitSeat` начинает с рекомендательной блокировки места `pg_advisory_xact_lock` (`ClassPolicy.lockSeat`). Модуль consent берёт её через порт `ClassAccessPort.lockSeat` и таблиц org не трогает. Ту же блокировку берут действия, которые отзывают доступ к месту: отзыв бумажного согласия, выпуск и перевыпуск карточки. Вход, начатый раньше отзыва, завершается до него, и отзыв завершает его сессию. Вход, начатый позже, ждёт и видит отзыв.
- **Выдача по заявкам закрывается вместе с сессиями.** `ACCOUNTS_PORT.revokeAllSessions` (identity) в той же транзакции вызывает `JoinGrants.close` (org): срок выдачи по одобренным и уже использованным заявкам аккаунта — `now()`. Заявки аккаунта находятся по частичному индексу `join_requests_account_grant_idx` (M1-56), а не полным просмотром таблицы.
- **Порядок блокировок везде один:** класс (строка `classes`, `FOR UPDATE`) → место (рекомендательная) → заявка (строка `join_requests`, `FOR UPDATE`). Поэтому взаимоблокировок нет.
- **Новые пути входа** (бот M8, iOS M6, Android M7) обязаны проходить `admitSeat` в транзакции выдачи сессии.

**Код класса и очередь заявок (ADR 0016 §6, M1-49).**
- Заявка по коду создаётся в транзакции под блокировкой строки класса — той же, что у одобрения и отказа. Под ней заявка перепроверяет код, переводит прежнюю ожидающую заявку того же устройства в `expired` и считает очередь.
- Ожидающих заявок в классе — не больше 40, сверх — 429 `join_queue_full` с `Retry-After: 30`. Предел точен при любой параллельности.
- Учитель гасит код сразу: `DELETE /classes/{id}/join-code` стирает хеш и срок кода и пишет в аудит `class.join_code_closed`. Заявка, которая нашла код до гашения, после него не создаётся. Уже поданные заявки остаются у учителя.
- Список заявок фильтрует статус в SQL с учётом срока. Диалог учителя (`status=pending`) получает не больше 40 строк.

**Башкирский текст на входе.** Литера класса, ФИО, должность, причина отказа и названия из справочника приводятся к канонической форме `@teletau/bashkir-text` до записи (`common/text.ts`, `normalizeClassLetter`, импорт справочника). Поиск школ сравнивает свёртку пакета; в SQL это функция `org_search_fold` (миграция 0004): `translate()` по его таблице `FOLD_MAP` и «№ 1» = «№1». По этому же выражению построены триграммные GIN-индексы, поэтому поиск идёт по индексу (проверка `EXPLAIN` — `m1-round2.test.ts`). Управляющие символы в свободном тексте — 422, ФИО — только русские и башкирские буквы, пробел, дефис и апостроф.

**Юридические документы.** Тексты версий — в `consent/legal-texts.ts` (единственный источник). API заносит версии в `legal_documents` при старте и заполняет `url` = `${PUBLIC_WEB_URL}/legal/<вид>/<версия>`. Страница веба по этому адресу читает текст из `GET /legal-documents/{kind}/{version}`. PDF карточек печатает действующий `consent_child` (ADR 0018).

**Проверки.**
- Матрица авторизации по всем операциям контракта — `apps/api/test/integration/authz-matrix.test.ts`.
- Сценарий демо на уровне API — `m1-flow.test.ts`.
- Гонки, сбои и краевые случаи по гейту M1:
  - `m1-round2.test.ts` (раунд 1): параллельные пачки на лимиты, `Idempotency-Key`, льготное окно refresh, Valkey недоступен, ошибка БД под перехватом логов;
  - `m1-round3.test.ts` (раунд 2): опросы заявки наперегонки с отзывом согласия и выпуском карточки, резерв F/P (30 верных QR одновременно, класс за NAT после опечаток, `Retry-After: 1`), матрица управляющих символов по всем операциям контракта;
  - `m1-final.test.ts` (раунд 3): 100 параллельных заявок по одному коду — ровно 40 ожидающих, замена заявки устройства, гашение кода (в том числе заявка, нашедшая код до гашения), `EXPLAIN` запроса `JoinGrants.close`.

### 6.10. Обучение, мотивация и дуэль (реализовано в M2)

- **Граф модулей** без циклов (`boundaries.mjs`): learning → content, corpus, consensus, progress; consensus → corpus, progress; progress → competition, org; competition → org (ники — через `ACCOUNTS_PORT`); content и corpus — листья. Вызовы между модулями — публичными сервисами в транзакции вызывающего (как `AuditService`): итог урока, мёд, очки лиги и активность класса пишутся в одной транзакции; outbox — в M4.
- **Часы.** Сутки и неделя — по Уфе (`@teletau/domain-rules` `calendar.ts`). Методы сервисов принимают момент `now` / `at` (контроллеры его не передают) — так тесты и демо-сид подменяют часы.
- **Правила** — чистые функции `packages/domain-rules` (`xp`, `streak`, `league`, `duel-v0`) и `matchAnswer` в `@teletau/bashkir-text`, с общими векторами `contracts/test-vectors/{answer-check,xp,streak,consensus}`. Ключи ответов не уходят клиенту: забег хранит план показа (`lesson_runs.plan`), ответ проверяется по нему.
- **Дуэль v0** (ADR 0019): `judgments` — только вставка (триггеры, как у `audit_log`), `item_state` пересчитывается из журнала, принятое решение закреплено до M4. Детям распределение голосов не показывается.
- **Демо-мир** (`apps/api/src/demo`, `pnpm demo:reset`): сид поднимает приложение в процессе, учётные записи и вход учеников делает запросами к нему (Fastify inject), историю уроков, голосов и лиги — публичными сервисами модулей с подменёнными часами. Для сида добавлен один публичный метод — `ClassesService.printJobCards` (полезные нагрузки карточек задания печати, проверки те же, что у PDF; операции контракта у него нет). Сквозные тесты работают на своей базе `<имя>_e2e` и пересоздают её с демо-миром на каждый прогон.

```
                     лимиты Bot API, очередь исходящих,
                     запуск Mini App
```

Сценарии: фраза дня, быстрая дуэль (2 кнопки + «оба верны»), напоминание о серии, рейтинг класса, команды учителя (`/класс`, `/битва`), дайджест родителя, запуск Mini App для полноценных уроков. Привязка Telegram-аккаунта — одноразовым кодом из приложения/веба (никаких данных из профиля Telegram не сохраняем, кроме технического `chat_id`). Ядро не зависит от Telegram: сценарии тестируются без него, а новый канал при необходимости добавляется адаптером. Меры на случай замедления Telegram — `08-infra-security-compliance.md` §8.

## 8. Мобильные приложения

### iOS
- Модули Swift Package: `DesignSystem` (токены, компоненты, Rive), `Networking` (сгенерированный клиент, авторизация, повтор запросов), `Persistence` (GRDB: контент, FSRS, журнал событий), `Sync`, `BashkirText` и `SRS` (порты с тест-векторами), `Features/*` (Onboarding, Home, LessonPlayer, Duel, PhraseOfDay, ClassHive, Profile, Parent, TeacherLite, Battle).
- Архитектура экранов: MVVM + однонаправленный поток (`@Observable` модели, `async/await`, `AsyncStream` для синхронизации).
- Нативные возможности: виджеты (WidgetKit — «Фраза дня», «Серия»), Live Activity для урок-битвы, Core Haptics, фоновая синхронизация (`BGAppRefreshTask`), App Intents («Начать урок»), панель башкирских букв как `inputAccessoryView`.
- Тесты: Swift Testing / XCTest на логику (включая тест-векторы), снапшот-тесты экранов в обеих темах и крупном шрифте, XCUITest для ключевых сценариев.

### Android
- Gradle-модули: `:app`, `:core:designsystem`, `:core:network`, `:core:database` (Room), `:core:sync` (WorkManager), `:core:bashkirtext`, `:core:srs`, `:feature:*`; convention plugins.
- Архитектура: MVVM/MVI — `ViewModel` + `StateFlow`, однонаправленные события, Hilt.
- Нативные возможности: Glance-виджеты, `VibrationEffect.Composition`, foreground-сервис не нужен (WorkManager), строка башкирских букв над клавиатурой, Baseline Profiles для быстрого старта.
- Сборки (product flavors) под RuStore, AppGallery, GetApps, Galaxy Store и Google Play; пуши — RuStore Universal Push SDK (RuStore + FCM + HMS) за интерфейсом `PushProvider`.
- Тесты: JUnit + тест-векторы, Roborazzi/Paparazzi снапшоты, Compose UI tests, Macrobenchmark для старта и прокрутки.

### Общее для мобильных
- Авторизация: короткоживущий access-токен + ротируемый refresh-токен, привязанный к устройству; хранение — Keychain / Android Keystore (EncryptedSharedPreferences/DataStore + Keystore).
- Аналитика и краши — только в собственный контур (без сторонних SDK, передающих данные за рубеж).
- Фичефлаги и удалённая конфигурация — с собственного API (кешируются офлайн).
- Принудительное обновление при несовместимости контракта (минимальная версия в конфиге).

## 9. Веб

- `apps/web`: публичный словарь и лендинги — SSR/ISR (индексация Яндексом), учебные экраны — клиентские, данные через клиент сессии `packages/session` (BFF, single-flight обновления), PWA с офлайн-кешем миссии дня. Telegram Mini App — тот же код в режиме `/miniapp` с адаптером Telegram WebApp SDK (тема, кнопка «назад», авторизация через проверку подписи `initData`).
- `apps/console`: отдельное приложение для внутренних ролей (иной профиль безопасности: обязательная 2FA, IP-ограничения для админов, расширенный аудит).
