# 03. Consensus Engine — согласование вариантов перевода

Сердце продукта. Задача: из голосов участников с разным уровнем знания языка (ученик A1, носитель-пятиклассник, учитель, эксперт-филолог) получить **надёжную** базу переводов, тратя минимум экспертного времени и не позволяя накручивать результат.

## 1. Ключевые сущности

| Сущность | Описание |
|---|---|
| `SourceItem` | Исходная единица: текст, язык (`ru`/`ba`), тип (слово / фраза / предложение / термин), домен (школа, быт, природа, IT, право…), сложность, источник и лицензия, приоритет, заказ (если есть) |
| `Variant` | Вариант перевода: текст, нормализованный текст, автор (или `origin = import / mt / llm`), метки (регистр: литературный / разговорный; диалект: южный / восточный / северо-западный; устаревшее), родительский вариант (если это правка) |
| `Judgment` | Неизменяемое событие оценки: тип (`approve`, `reject`, `unsure`, `pairwise(winner, loser, tie)`, `edit`, `flag`, `expert_decision`), судья, контекст (задание, контрольное ли, время ответа, устройство), снимок веса судьи на момент голоса |
| `ItemState` | Производное состояние исходника: статус, апостериорные оценки вариантов, множество принятых вариантов, «основной» вариант, уверенность, причины решения |
| `Reliability` | Модель надёжности участника по (направлению × домену): чувствительность α и специфичность β с байесовскими априорными, история контрольных заданий |
| `GoldItem` | Контрольное задание: вариант с известной (экспертной) истиной |
| `Release` | Версионированный снимок принятых пар для API/датасета |

**Принцип event sourcing:** `Judgment` никогда не изменяется и не удаляется (кроме удаления по запросу субъекта ПДн — тогда судья обезличивается, но голос остаётся). `ItemState` всегда можно пересчитать из журнала голосов — значит, при улучшении алгоритма мы пересчитываем всю базу и видим, какие решения поменялись бы.

## 2. Жизненный цикл исходника

```
           ┌──────────┐  есть ≥1 вариант   ┌──────────────┐
  создан → │ COLLECT  │ ─────────────────→ │   VOTING     │
           └──────────┘                    └──────┬───────┘
                ▲                                 │
                │ все варианты отклонены          ├── P(верно) ≥ порога, кворум → ACCEPTED
                └─────────────────────────────────┤
                                                  ├── спор / застой / термин / жалоба → ESCALATED
                                                  │                                        │
                                                  │                   решение эксперта ────┘
                                                  ▼
                                        ACCEPTED ──(релиз)──→ PUBLISHED
                                           │
                                           └── апелляция / новый сильный вариант → DISPUTED → VOTING
```

У исходника может быть **несколько принятых вариантов** (синонимия, регистры, диалекты). «Основной» — лидер попарного рейтинга среди принятых.

## 3. Модель надёжности участника

Для каждого участника `u` и среза `s` (направление × домен; при нехватке данных — откат к общему срезу):

- α_u — вероятность сказать «верно», если вариант действительно верен (чувствительность);
- β_u — вероятность сказать «неверно», если вариант действительно неверен (специфичность).

**Априорные распределения по роли** (Beta, затем обновляются данными):

| Роль | α ~ Beta | β ~ Beta | Смысл |
|---|---|---|---|
| Эксперт | (38, 2) | (38, 2) | ≈95% |
| Учитель башкирского | (18, 2) | (17, 3) | ≈90%/85% |
| Ученик-носитель | (12, 3) | (10, 4) | ≈80%/71% |
| Взрослый ученик B1+ | (8, 3) | (7, 4) | ≈73%/64% |
| Ученик A1–A2 | (6, 4) | (5, 5) | ≈60%/50% |
| Новичок без данных | (5, 5) | (5, 5) | монетка |

**Обновление:**
1. **Онлайн** — после каждого контрольного задания и каждого финального решения (с задержкой: голос учитывается для оценки надёжности только после того, как исходник принят/отклонён *без* участия этого голоса в кворуме — защита от самоподтверждения).
2. **Пакетно** (ночью, `apps/ml-worker` на TypeScript) — EM-алгоритм Dawid–Skene по всей матрице «участник × вариант» с учётом априорных; результат заменяет онлайн-оценки.

**Вес голоса** (логарифм отношения правдоподобий):

```
w_approve(u) = ln( α_u / (1 − β_u) )
w_reject(u)  = ln( (1 − α_u) / β_u )      // отрицательный
w_unsure     = 0
```

Дополнительные множители (≤ 1): слишком быстрый ответ (время < медианы × 0,3) → 0,3; участник из того же класса, что и автор варианта → 0 (голос сохраняется, но в кворуме не участвует); подозрение на сговор → 0 до проверки.

## 4. Оценка варианта

Логарифм шансов «вариант верен»:

```
L(v) = L_prior(v) + Σ_j w_j(v)
P(v) = σ(L(v))
```

`L_prior(v)` — автоматические сигналы (каждый — признак в маленькой логистической модели, обученной на экспертной разметке пилота):

| Сигнал | Смысл |
|---|---|
| Проверка алфавита | Только допустимые символы, нет смешения латиницы и кириллицы |
| Орфография | Доля слов, известных спеллеру GiellaLT `speller-bak` (FST, ≈35 тыс. лемм; LGPL — подключается отдельным сервисом) и словарю принятых вариантов |
| Отношение длин | Сильное отклонение от типичного для пары рус↔баш |
| Семантическая близость | LaBSE-bak (Apache-2.0): близость исходника и варианта в общем векторном пространстве — грубый фильтр качества (порог ≈ 0,8 применялся для чистки корпусов) |
| Обратный перевод (GigaChat) | Семантическая близость обратного перевода к исходнику (эмбеддинги) |
| Детектор дрейфа | Татарские и казахские буквы и формы (`04-ai-gigachat.md` §5.4) |
| Совпадение с базой | Близость к уже принятым вариантам похожих исходников |
| Происхождение | `import` из проверенного словаря — плюс; `llm`/`mt` — нейтрально или минус |
| Репутация автора | Надёжность автора как переводчика |

Важно: автоматические сигналы **только сдвигают априорную оценку**, они не могут сами по себе принять вариант — для принятия всегда нужен человеческий кворум.

**Попарные дуэли** дают отдельную шкалу — рейтинг Bradley–Terry (с весами судей) между вариантами одного исходника. Он отвечает на вопрос «какой вариант лучше/естественнее», а не «верен ли». Победа в дуэли также даёт слабый сигнал в `L(v)` для обоих участников дуэли (проигравший не обязательно неверен).

## 4a. Три группы голосов и их приоритет (решение владельца)

Ответы собираются и показываются **раздельно по группам**: что ответили **дети**, что **учителя**, что **взрослые**. Группа берётся из типа аккаунта на момент голоса и пишется в неизменяемый `Judgment` (поле `voter_group`: `child` | `teacher` | `adult`; эксперты — отдельная роль `expert`). ПДн для этого не нужны.

**Приоритет:** эксперт (решающее слово) > учитель > взрослый > ребёнок. Он работает на трёх уровнях:
1. **Вес голоса** — уже через априорные надёжности §3: у учителя они выше, чем у взрослого, у взрослого — выше, чем у ребёнка того же уровня.
2. **Кворум (§5):** голосами одних детей вариант не принимается — нужен хотя бы один голос учителя или взрослого с надёжностью ≥ 0,8 (или решение эксперта).
3. **Конфликт групп:** для каждой группы отдельно считается `P_g(v)` (та же модель, только голоса группы). Если уверенные группы расходятся (одна ≥ 0,9, другая ≤ 0,1), побеждает группа с более высоким приоритетом, а при расхождении **учителей и взрослых** исходник уходит эксперту.

**В дуэлях «какой перевод естественнее»** расхождение детей и взрослых — не ошибка, а ценный сигнал: «так говорят дети» помечается меткой варианта (`tags: ["children_prefer"]`), а главным вариантом остаётся выбор старших групп.

**Где голосует каждая группа:** дети — дуэли и проверки внутри уроков (приложения, веб, мини-приложение); учителя — консоль учителя и Telegram-бот; взрослые — веб и приложения во взрослом режиме, Telegram-бот.

## 5. Правила решений

| Решение | Условие (стартовые пороги, калибруются на пилоте) |
|---|---|
| **ACCEPT** | P(v) ≥ 0,95 **и** ≥ 3 учтённых голоса «за» **и** голоса минимум из 2 разных школ **и** ≥ 1 голос учителя или взрослого с надёжностью ≥ 0,8 (голосами одних детей не принимается, §4a) |
| **REJECT** | P(v) ≤ 0,05 и ≥ 3 учтённых голоса |
| **ESCALATE** | (а) 9+ голосов без решения; (а′) уверенные учителя и взрослые расходятся (§4a); (б) высокая энтропия между двумя сильными вариантами с противоречивыми дуэлями; (в) тип = термин (всегда); (г) ≥ 2 жалобы; (д) заказ партнёра с флагом «требуется эксперт»; (е) случайная выборка 3% принятых — для аудита качества |
| **EXPERT DECISION** | Финальное; эксперт может принять несколько вариантов, отредактировать, добавить метки. При решении против взвешенного большинства — обязательный комментарий |
| **REOPEN** | Апелляция взрослого участника с аргументом, принятая модератором, или новый вариант, который в дуэлях стабильно побеждает основной |

Пороги хранятся в конфигурации (по типу исходника и домену) и версионируются: каждое решение помнит версию правил.

## 6. Маршрутизация заданий (кому что показать)

Цель — максимум информации на один голос при сохранении учебной ценности.

1. **Кандидаты:** исходники в статусе VOTING/COLLECT, лексически доступные ученику (≥90% лемм известны по FSRS), не его собственные варианты, не варианты одноклассников.
2. **Ожидаемый прирост информации:** для каждого кандидата — ожидаемое снижение энтропии статуса при голосе судьи с надёжностью (α, β); умножается на приоритет исходника (заказ Фонда > школьная лексика > общий пул) и на «срочность» (сколько ждёт).
3. **Разнообразие:** не более N голосов за исходник от одной школы; дуэли показываются в случайном порядке сторон (защита от позиционного смещения).
4. **Контрольные задания:** 10–15% заданий корпусного типа — `GoldItem`, неотличимые от обычных. Доля выше для новичков и падает с ростом надёжности.
5. **Носители и учителя** получают в первую очередь исходники в COLLECT (нужен вариант) и ESCALATED-кандидаты (снимают нагрузку с экспертов).
6. **Ограничения дня:** у ученика корпусные задания ≤ 40% миссии (учёба важнее).

## 7. Антифрод

| Угроза | Детекция | Реакция |
|---|---|---|
| Сговор класса для накрутки рейтинга | Голоса одноклассников за варианты одноклассников не учитываются; граф «кто за кого голосует» — поиск плотных клик | Обнуление весов группы до ручной проверки |
| Голоса «не глядя» | Время ответа, доля контрольных ошибок, всегда одна сторона в дуэлях | Снижение веса до 0; мягкое сообщение «давай внимательнее» |
| Мультиаккаунты | Отпечаток устройства (без ПДн), одинаковые паттерны ответов | Объединение весов, проверка модератором |
| Вандализм (мат, мусор) | Фильтры (рус/баш словари), модерация GigaChat, жалобы | Скрытие варианта, предупреждение, блокировка |
| Систематическая ошибка группы (например, весь класс учит один неверный вариант от учителя) | Расхождение с экспертным аудитом, кластерный анализ | Эскалация исходников кластера, уведомление методисту |
| Отравление базы машинными переводами | Детектор «машинности» (совпадение с выдачей MT), происхождение `llm/mt` не даёт бонус | Отметка, повышенный кворум |

## 8. Прозрачность — карточка происхождения

У каждой принятой пары — публичная карточка: исходник, варианты, статус, дата, голоса **раздельно по группам** — дети, учителя, взрослые, эксперты: «за» / «против» / «не уверен» и доля в дуэлях (без ников детей), уверенность, было ли экспертное решение (и кто из экспертов, если эксперт согласился на публичность), версия правил, история изменений. В API это поле `provenance`.

## 9. Релизы датасета

- Ежемесячно (и по запросу для заказов): снимок ACCEPTED/PUBLISHED пар → валидация (дубли, алфавит, баланс доменов) → отчёт о качестве (объём, доля экспертных решений, точность выборочного аудита, согласие судей — Криппендорф α) → публикация (JSONL, TSV, TMX, XLSX + манифест с контрольными суммами) → changelog (добавлено / изменено / отозвано).
- Семантическое версионирование: `2027.03.0`; отозванные пары помечаются, а не удаляются из истории.

## 10. Метрики качества движка

| Метрика | Цель |
|---|---|
| Точность ACCEPT по выборочному экспертному аудиту | ≥ 95% |
| Полнота (доля верных вариантов, не отклонённых) | ≥ 90% |
| Медианное время от появления варианта до решения | ≤ 72 ч |
| Доля эскалаций | ≤ 15% |
| Голосов на решение (медиана) | ≤ 5 |
| Калибровка (P(v) vs фактическая точность) | ECE ≤ 0,05 |

## 11. Как проверяем движок до запуска

1. **Симулятор** (TypeScript, `apps/ml-worker`): синтетические участники с заданными α/β, ролями, долей злоумышленников и сговорщиков; синтетические исходники с известной истиной. Прогон тысяч сценариев → графики точности/стоимости в зависимости от порогов. Симулятор — часть CI (регресс по метрикам).
2. **Тест-векторы** (`contracts/test-vectors/consensus/*.json`) — детерминированные кейсы «журнал голосов → ожидаемое состояние» для регресса.
3. **Пилот**: эксперты размечают 2 000 вариантов — калибровка порогов и логистической модели автоматических сигналов.
4. **Постоянный аудит**: 3% принятых → эксперту вслепую.

## 12. Реализация

- Онлайн-часть (подсчёт `L(v)`, правила решений, маршрутизация) — модуль `consensus` в основном API (TypeScript), транзакционно с записью голоса.
- Пакетная часть (Dawid–Skene EM, Bradley–Terry, обучение модели автоматических сигналов, симулятор, детектор сговора) — TypeScript-сервис `apps/ml-worker`, запуск по расписанию и по событию. Dawid–Skene (EM) и Bradley–Terry (MM-алгоритм) — компактные итеративные алгоритмы, реализуем сами; корректность проверяется тест-векторами на синтетических данных симулятора с известной истиной (по мотивам эталонной библиотеки `crowd-kit`). Онлайн-рейтинг вариантов в дуэлях — OpenSkill (модели Weng–Lin, MIT) вместо TrueSkill (патентная чистота TrueSkill не подтверждена).
- **Стартовый пул исходников и кандидатов:** параллельный корпус AigizK (≈1,2 млн пар рус–баш, CC-BY-4.0) импортируется как `origin = import` — это кандидаты, а не подтверждённые пары. Ученики и носители сразу получают задания «верен ли перевод» и дуэли на реальном материале. Из шумного корпуса получается его вычищенное, подтверждённое людьми подмножество — ценный результат с первого дня.
- Состояния кешируются в PostgreSQL (`item_state`), события — в таблице `judgments` (секционирование по месяцам) и дублируются в ClickHouse для аналитики.
