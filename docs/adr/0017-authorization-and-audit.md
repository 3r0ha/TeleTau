# ADR 0017. Авторизация (RBAC + ABAC, матрица по контракту) и журнал аудита только для вставки

- Статус: принято (M1, фаза 1; реализация — T5)

## Контекст
С M1 в системе появляются ученики, учителя, модераторы и администраторы, а также данные классов. Главная угроза по `docs/08` §6 — IDOR: доступ к чужому классу или ребёнку. ASVS L2 требует проверять доступ на каждой операции и вести неизменяемый журнал действий сотрудников. Ручные проверки «по месту» расползаются и забываются в новых эндпоинтах.

## Решение

### 1. RBAC
- **Вид аккаунта** (`kind`): `child`, `adult`, `staff`.
- **Роли** (`accounts.roles`, утверждение `roles` в JWT): `student`, `teacher`, `moderator`, `admin`.

Роль `teacher` появляется только после одобрения заявки модератором. До этого учитель — просто `adult`: «учитель на проверке» — это взрослый с заявкой в статусе `pending`, его статус показывает `GET /me` → `teacherStatus`.

### 2. ABAC
Политики — функции в публичных сервисах модулей. Контроллер их не реализует, только вызывает.

| Политика | Кто проходит |
|---|---|
| `class-teacher` | владелец класса |
| `class-member` | учитель класса или ученик с местом в нём |
| `self` | только свои данные |
| `consent-owner` | взрослый-субъект согласия или учитель класса, если согласие бумажное |
| `poll-token` | предъявитель секрета опроса заявки |

### 3. Правило доступа в контракте
Каждая операция `openapi.yaml` несёт `x-access: { roles, policy }`. `pnpm contracts:check` (`packages/contracts/scripts/access-rules.mjs`) проверяет:
- у каждой операции есть `x-access`;
- роли и политики известны;
- `security` согласован с ролью `anonymous`;
- объявлены ответы, которых требует правило:
  - закрытая операция — 401;
  - ограничение по роли или политике — 403;
  - параметры пути — 404;
  - тело запроса — 422.

### 4. Матрица авторизации
Матрица — тест API (T5). Для **каждой** операции контракта он проверяет три случая:

| Случай | Ответ |
|---|---|
| аноним | 401 |
| чужая роль | 403 |
| чужой ресурс | 403 |

Если операция из `openapi.yaml` (по `operationId`) не попала в матрицу, тест падает.

**404 вместо 403** — только там, где само существование ресурса — секрет. Это заявка на вход при неверном `X-Poll-Token`. Чужой класс — 403, как требует критерий приёмки 4.

### 5. Журнал аудита
- **Таблица.** `audit_log` в модуле `admin` — только вставка. UPDATE, DELETE и TRUNCATE запрещены триггерами, которые срабатывают и для владельца таблицы (миграция `0002_m1_guards`).
- **Роль приложения.** Миграция создаёт роль `teletau_app`: SELECT, INSERT, UPDATE, DELETE на таблицы `public` и `pii`, но на `audit_log` — только SELECT и INSERT. В проде API подключается логин-ролью из `teletau_app` и не владеет таблицами. Миграции идут под ролью-владельцем. Интеграционный тест (`apps/api/test/integration/m1-schema.test.ts`) проверяет оба уровня защиты.
- **Запись.** Модули пишут в журнал через публичный сервис модуля `admin` в той же транзакции, что и само изменение: изменение без записи в аудит невозможно.
- **Содержимое строки.** `metadata` — объект без ПДн, секретов и токенов: номер места, версия карточки, причина. Вместо IP хранится `ip_hash` = HMAC-SHA-256(`AUTH_SECRET_PEPPER`, IP).
- **Действия M1:** `card.issued`, `card.reissued`, `class.join_code_issued`, `class.join_code_closed`, `join_request.approved`, `join_request.rejected`, `teacher_verification.submitted`, `teacher_verification.approved`, `teacher_verification.rejected`, `consent.given`, `consent.revoked`, `session.refresh_reuse_detected`, `session.device_mismatch`, `staff.login`, `staff.login_failed`, `staff.locked`. Формат `<объект>.<событие>` проверяет CHECK в базе.
- **Чтение.** Читают журнал `moderator` и `admin` (`GET /admin/audit-log`).

### 6. ПДн детей на уровне базы
В `pii.adult_profiles` нельзя вставить строку для детского аккаунта, а аккаунт с такой строкой нельзя сделать детским. Это обеспечивают триггеры той же миграции (ADR 0009).

## Последствия
- **Новый эндпоинт** без `x-access` не пройдёт `contracts:check`, а без строки матрицы — тесты API.
- **Подключение в dev.** В dev API пока подключается владельцем `teletau`. Триггеры защищают журнал и так, но владелец мог бы отключить триггер DDL-командой. Переход dev и CI на логин-роль из `teletau_app` сделаем вместе с ролями модулей из ADR 0014 — до M4.
- **Новые таблицы только для вставки** (например, `judgments` в M4) повторяют схему: триггер и REVOKE для `teletau_app`.
- **Рост журнала.** Журнал растёт бессрочно. Помесячное секционирование — в M11.

## Альтернативы
- **Проверки доступа в guard'ах по декораторам** без политик в сервисах — отклонено: проверка ресурса («класс этого учителя») всё равно требует данных модуля.
- **Аудит через outbox асинхронно** — отложено: в M1 нужна атомарность с изменением. Outbox появится вместе с доменными событиями.
- **Только права роли без триггера** — отклонено: в dev и тестах подключение идёт владельцем, и защита должна действовать везде.

## Уточнения реализации (M1, T5)
- **Где проверяется роль.** `x-access` берётся из контракта во время выполнения (`@teletau/contracts/openapi.json`, декоратор `@Operation`). Роль проверяется в хуке Fastify `onRequest` (`apps/api/src/modules/identity/access-control.ts`) — до разбора и проверки тела: аноним получает 401, а не 422. Nest-guard — страховка: обработчик без пройденного хука не выполняется.
- **Направление зависимостей модулей.** Граф: identity → moderation → org → consent → admin. Обратные потребности объявлены портами в `apps/api/src/common/ports.ts`: `ACCOUNTS_PORT` реализует identity, `CLASS_ACCESS_PORT` — org, `TEACHER_SCHOOL_PORT` — moderation. Так нет циклов импорта, и модуль не читает чужие таблицы.
- **Должность заявителя — ПДн.** Она хранится в `pii.adult_profiles.position` (миграция 0003). `teacher_verifications.position` устарела и всегда NULL (CHECK).
- **Матрица** — `apps/api/test/integration/authz-matrix.test.ts`. Тест сверяет строки с `x-access`: роль «чужой роли» не должна быть разрешена контрактом, а роль «чужого ресурса» — должна.

## Уточнения по гейту M1, раунд 1 (доработка)
- **Причина отказа модератора — в схеме `pii` (M1-22).** Это свободный текст, и в нём бывают ПДн заявителя. Причина хранится в таблице модуля moderation `pii.teacher_verification_reasons` (по строке на отклонённую заявку), миграция 0004 переносит туда старые причины. `teacher_verifications.decision_reason` устарела и всегда NULL (CHECK), удаляется контрактной миграцией в M11. В аудит текст причины по-прежнему не пишется.
- **Новое действие `staff.locked`** — вход сотрудника заблокирован на час после 10 неверных TOTP за час (ADR 0015).
- **`card.reissued`** несёт `metadata.sessionsRevoked` — сколько семейств сессий ученика завершено перевыпуском (ADR 0016 §3).
- **`session.refresh_reuse_detected`** пишется один раз на семейство (ADR 0015): журнал только для вставки, и один украденный токен не должен его засорять.
- **Матрица авторизации** не изменилась: новых операций нет, новый необязательный заголовок `X-Device-Install-Id` у `getClassCodeLoginStatus` политику `poll-token` не меняет.

## Уточнение: роли министерства и Фонда (ADR 0023)
- **Новые роли сотрудника** — `ministry` (кабинет министерства, только агрегаты) и `fund` (словарь для Фонда). Их
  операции открыты только своей роли; администратор и модератор их не получают автоматически.
- **В контракте** перечисление `Role` закрыто базовой версией M1, поэтому новые роли приходят в расширяемом
  `StaffRole` — полях `Me.staffRoles` и `AuditActor.staffRoles`; в `roles` ответов — только прежний набор.
- **Матрица** дополнена четырьмя операциями: `getRepublicSummary`, `listRepublicDistricts`, `getRepublicDistrict`,
  `getFundDictionary`.
