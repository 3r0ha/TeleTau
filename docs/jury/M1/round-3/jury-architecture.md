## Находки

### [P3] 1. Перегрузка Postgres отвечает 500 `internal`, а не 503: ребёнок видит «Что-то сломалось», в журнал на каждый запрос пишется ERROR со стеком
- **Где:**
  - `apps/api/src/common/problem.filter.ts:153` — всё, кроме `ApiError`, HttpException и ошибок Fastify, становится 500 `internal`;
  - `apps/api/src/infra/clients.ts:15-16` — пул `max: 10`, `connectionTimeoutMillis: 2000`;
  - для сравнения: сбой Valkey отвечает 503 (`apps/api/src/infra/rate-limiter.ts:144-150`).
- **Доказательство:** второй экземпляр API (порт 38001) я подключил к Postgres через TCP-прокси, который добавляет 40 мс к каждому пакету в обе стороны. Сценарий `storm.mjs`: 99 настоящих карточек из PDF, все одновременно, с одного IP.
  ```
  без задержки: "qrBurst": {"validCards":99,"responses":{"200":99}}
  +40 мс:       "qrBurst": {"validCards":99,"responses":{"200":30,"500 internal":20,"429 rate_limited ra=1":49}}
  ```
  В журнале:
  - 20 раз: `ERROR [ProblemFilter] POST /api/v1/auth/qr → 500: DrizzleQueryError (select "seat_cards") ← caused by Error: timeout exceeded when trying to connect`;
  - для одобрений заявок: `SQLSTATE=57014` (statement_timeout);
  - всего 107 строк ERROR со стеком примерно за 20 с, без прореживания (ошибки инфраструктуры прореживаются до раза в 30 с).

  Ребёнку показывается `packages/session/src/problem.ts:113`: «Что-то сломалось. Мы уже чиним — попробуй ещё раз».
- **Почему это проблема:** исчерпание пула, `statement_timeout` и `lock_not_available` — временная перегрузка, а не ошибка в коде. Клиенты и BFF не могут отличить «повторите через секунду» от бага. Мониторинг утром 1 сентября увидит всплеск 500 вместо 503, а журнал забивается стеками ровно тогда, когда базе и так тяжело. При обычной задержке базы проблема не проявляется, поэтому это P3.
- **Предлагаемое исправление:** в `ProblemFilter` распознавать временные отказы БД:
  - таймаут получения соединения из пула;
  - SQLSTATE `57014`, `55P03`, `40001`, `40P01`, `53300`.

  Ответ на них — 503 `service_unavailable` с `Retry-After: 1–2` и прореженной строкой WARN через `reportInfraError`. Тест — с TCP-прокси из `resilience.test.ts`.

### [P3] 2. Клиент теряет `Retry-After`: при `429 Retry-After: 1` (M1-36) ребёнок с верной карточкой читает «Слишком много попыток. Подожди минуту»
- **Где:**
  - `packages/session/src/client.ts:45` — `throw new ApiProblem(res.status, data)`: заголовки ответа отбрасываются;
  - `packages/session/src/problem.ts:4-16` — у `ApiProblem` нет поля `retryAfter`;
  - `packages/session/src/problem.ts:45,109` — на любой 429 один текст;
  - вызовы — `apps/web/app/student/qr.ts:108-109`, `apps/web/app/student/code/page.tsx:148-154`.
- **Доказательство:**
  - Сервер теперь различает два отказа (ADR 0016, уточнения раунда 2): «неудачи исчерпаны» — остаток окна, «мешают только попытки в работе» — `Retry-After: 1`.
  - BFF передаёт заголовок браузеру (`packages/session/src/server.ts:99-102`, ADR 0015:114).
  - Браузерный клиент заголовок не читает. В прогоне с задержкой из находки 1 49 детей с верными карточками получили `429 rate_limited ra=1`. Каждому показали бы «Слишком много попыток. Подожди минуту и попробуй снова», хотя попытка была одна.
- **Почему это проблема:** исправление M1-36 на сервере сделано именно для того, чтобы короткая очередь не выглядела как блокировка за подбор. До пользователя это различие не доходит, и текст ошибки неверен. Клиенты M6/M7 будут реализовывать тот же контракт, а договорённость о `Retry-After` нигде не записана.
- **Предлагаемое исправление:**
  - сохранять `Retry-After` в `ApiProblem`;
  - при `Retry-After ≤ 5` молча повторять запрос один-два раза, затем показывать «Секунду, много входов — попробуй ещё раз», а не «подожди минуту»;
  - записать правило в docs/07 (раздел об ошибках), чтобы iOS и Android повторили то же;
  - тест на моках веба: 429 с `Retry-After: 1`, затем 200 — вход проходит без текста ошибки.

### [P3] 3. `JoinGrants.close` — полный просмотр `join_requests` на каждом отзыве сессий, под блокировками класса и места; таблица не чистится
- **Где:**
  - `apps/api/src/modules/org/join-grants.ts:21-27` — `UPDATE join_requests … WHERE account_id = $1 AND status IN ('approved','consumed') AND expires_at > now()`;
  - `apps/api/src/modules/org/org.schema.ts:206-207` — индексы только по `poll_token_hash` и `(class_id, status, created_at)`, по `account_id` индекса нет;
  - вызывается из `revokeAllSessions` (`identity/accounts.service.ts:142`):
    - перевыпуск — `org/classes.service.ts:254`, под `lockTeacherClass` (`FOR UPDATE` класса) и блокировкой места;
    - отзыв согласия — `consent/consent.service.ts:336`;
    - блокировка — `identity/staff-seed.ts:59`.
- **Доказательство:** в изолированной базе 300 тыс. строк `join_requests`, `EXPLAIN ANALYZE` в откатываемой транзакции:
  ```
  без индекса:  Seq Scan on join_requests … Rows Removed by Filter: 300467   Execution Time: 166–455 ms
  с (account_id) WHERE account_id IS NOT NULL:  Index Scan using tmp_jr_account …   Execution Time: 0.550 ms
  ```
  Строки `join_requests` не удаляются: M1-48 перенесена в M9.
- **Почему это проблема:** перевыпуск даже для ученика, который ни разу не входил по коду, держит блокировку класса на время полного просмотра. Всё это время одобрения заявок, выпуск карточек и вход на это место ждут. Таблица растёт монотонно, так что время перевыпуска растёт вместе с числом всех заявок в республике. В пилотных объёмах незаметно, отсюда P3.
- **Предлагаемое исправление:** аддитивная миграция — частичный индекс `join_requests (account_id) WHERE status IN ('approved','consumed')`, в проде создавать `CONCURRENTLY`. Тест в духе `EXPLAIN` из `m1-round2.test.ts`. Если в M9 появится чистка заявок старше суток (M1-48), индекс останется полезным, но перестанет быть срочным.

### [P3] 4. docs/06 §6.9 описывает лимиты раунда 1 и не знает о механизмах раунда 3
- **Где:**
  - `docs/06-architecture.md:252` — «один Lua-скрипт «сравнение с лимитом + INCR»… резервируются до проверки и возвращаются». Сейчас два счётчика F и P, ожидание до 2 с и `Retry-After: 1`;
  - `docs/06-architecture.md:234` — шаг 3 «ajv», но до него теперь стоит хук `preValidation` с проверкой управляющих символов (`bootstrap.ts`, M1-40);
  - `docs/06-architecture.md:263` — тесты гонок и сбоев указаны только в `m1-round2.test.ts`, без `m1-round3.test.ts`;
  - в §6.9 нет блокировки места (`admitSeat`, `ClassAccessPort.lockSeat`) и `JoinGrants`, хотя это сквозное решение для трёх модулей.
- **Доказательство:** `grep -n "admitSeat\|lockSeat\|JoinGrants\|m1-round3" docs/06-architecture.md` — пусто. ADR 0015:128-129 и ADR 0016:128-146 всё это описывают.
- **Почему это проблема:** docs/06 — точка входа для нового человека в команде. Описание лимитера в ней прямо противоречит коду, а правило «вход и отзыв доступа к месту берут одну блокировку» придётся соблюдать при появлении новых путей входа (бот M8, мобильные M6/M7).
- **Предлагаемое исправление:** обновить три строки §6.9 и добавить абзац «Вход на место»: `admitSeat`, блокировка места, `JoinGrants.close` в `revokeAllSessions`, порядок блокировок «класс → место → заявка» — со ссылкой на ADR 0016.

## Что сделано хорошо (≤ 5 пунктов)
1. **Одна проверка входа и одна блокировка.** `admitSeat` вызывают оба пути входа. Отзыв согласия, перевыпуск и вход сериализованы `pg_advisory_xact_lock` по месту, а модуль consent берёт её через порт и таблиц org не касается. Гонку я проверил вживую.
2. **Лимитер с явным исходом.** Счётчики F и P живут в одном Lua-скрипте, `fail()`/`release()` вызываются ровно один раз, исключение посередине неудачей не считается, у попыток «в работе» свой срок жизни. При этом гарантия M1-05 («ровно `max` неудач») сохранилась до единицы.
3. **Обоснование лимитов в ADR.** Расчёт вероятности угадывания (32⁶, 1 500 кодов на адрес, 1,4·10⁻³ при тысяче открытых кодов) и роль одобрения учителем записаны в ADR 0016 §6, а не только в коде.
4. **Тесты сначала.** 20 из 21 нового интеграционного теста падали до исправления. Матрица управляющих символов строится по `contractOperations()` и сама подхватит новые операции.
5. **Защита M1-40 на входе.** Управляющие символы отсекаются хуком `preValidation` до схемы и обработчика, поэтому код из письма больше не сгорает на 500.
