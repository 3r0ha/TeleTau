## Находки

### [P1] Повторный опрос заявки по коду класса выдаёт новую сессию после отзыва согласия и после перевыпуска карточки
- **Где:**
  - `/Users/kitty/Cyber102/Project2/apps/api/src/modules/org/join.service.ts:136-147`: выдача сессии `grant` при опросе (и первая, и повторная `repeat`, добавленная для M1-07). Проверяются только устройство и срок заявки.
  - `/Users/kitty/Cyber102/Project2/apps/api/src/modules/identity/student-login.service.ts:113-123`: сессия выпускается без `consents.isSeatBlocked`. Для сравнения, вход по QR проверяет согласие в `:70`.
  - Отзыв сессий (`consent.service.ts:332`, `classes.service.ts:243`) заявки этого аккаунта не закрывает.
  - Демо §6.3–§6.4 и ADR 0016:114 обещают, что ученик выходит на всех устройствах и вход закрыт.
- **Доказательство:** изолированный стек `jsec2`, скрипты `/private/tmp/claude-501/-Users-kitty-Cyber102-Project2/31d359a7-fccf-4e16-be4e-3fb3701df9ee/scratchpad/jsec2/scripts/probe-poll-bypass.mjs` и `probe-poll-first.mjs`:
  ```
  A3 учитель отзывает бумажное согласие места                    200
  A4 GET /me сессией 1 после отзыва                              401
  A6 повторный опрос той же заявки (тот же X-Poll-Token и устройство) 200 status=approved session=true
  A7 GET /me новой сессией (согласие отозвано!)                  200
  A9 refresh новой сессии                                        200 refreshTokenExpiresAt=…
  B4 перевыпуск (v2) — должен выгнать                            200
  B5 GET /me старой сессией после v2                             401
  B6 повторный опрос после перевыпуска                           200 status=approved session=true
  ---
  учитель отозвал согласие места до первого опроса             200
  первый опрос ученика                                         200 status=approved session=true
  для сравнения: вход по QR этого же места                     403 consent_revoked
  ```
- **Почему это проблема:**
  - Оба способа учителя выгнать ученика (отзыв согласия по заявлению родителя и перевыпуск) отменяются за один запрос. Хватает `X-Poll-Token` и `installId`, а окно — 15 минут после одобрения.
  - Новая сессия получает полный срок: 30 дней скользящий, 90 дней абсолютный, обновления работают.
  - Реалистичный сценарий: код класса висит на доске, учитель по ошибке одобрил чужой ник. Выгнать постороннего он не может (см. также P2).
  - Если согласие отозвано до первого опроса, ребёнок всё равно входит, хотя QR этого же места отвечает 403. Это та же проблема, что M1-03, только через другой путь входа.
  - Тест M1-07 (`m1-round2.test.ts:277-316`) отзыв не проверяет.
- **Предлагаемое исправление:**
  - В `StudentLoginService.poll` перед любой выдачей проверять `consents.isSeatBlocked(seatId)` и архивность класса — так же, как в QR-входе.
  - В транзакциях `reissue` и `consent.revoke` закрывать выдачу по заявкам этого аккаунта: публичный метод org, например `join.closeGrants(tx, accountId)`, ставит `expires_at = now()`.
  - Тесты:
    - одобрение → опрос → отзыв согласия → повторный опрос: сессии нет;
    - то же для перевыпуска v2;
    - отзыв согласия до первого опроса → 403 `consent_revoked`.

### [P2] Для места, занятого по коду класса, «Перевыпустить карточку» обещает «Ученик выйдет на всех устройствах», но сессии не завершаются
- **Где:**
  - `/Users/kitty/Cyber102/Project2/apps/web/app/teacher/classes/[id]/SeatDialog.tsx:129-133`: текст показывается при любом `seat.student`, в том числе при `cardStatus: none`, и кнопка та же (`:167-168`).
  - `/Users/kitty/Cyber102/Project2/apps/api/src/modules/org/classes.service.ts:241-243`: `if (version > 1 && seat.accountId)`, то есть первая карточка места сессий не трогает.
- **Доказательство:** `probe-poll-bypass.mjs`, шаги B2–B3: «первая карточка места (v1) 200», затем `GET /me` старой сессией — 200.
- **Почему это проблема:** учитель уверен, что выгнал вошедшего по коду (возможно, постороннего), а тот остаётся в классе. Довод в коде («старой карточки не было») верен для кражи карточки, но не для выселения. Другого действия «убрать ученика с места» в M1 нет.
- **Предлагаемое исправление:** при выпуске первой карточки на место с аккаунтом тоже вызывать `revokeAllSessions(…, "card_reissued")`: законный ученик войдёт по новой карточке. Либо для `cardStatus: none` показывать честный текст и отдельное действие «Завершить сессии ученика». Добавить тест.

### [P3] В окне запуска Next.js BFF принимает адрес клиента из подставленного заголовка `x-teletau-peer-address`
- **Где:**
  - `/Users/kitty/Cyber102/Project2/packages/session/src/peer.ts:19-27`: патч `Server.prototype.emit` ставится из `instrumentation.ts` (`/Users/kitty/Cyber102/Project2/apps/web/instrumentation.ts:3-7`).
  - `/Users/kitty/Cyber102/Project2/packages/session/src/client-ip.ts:124-126`: значение заголовка принимается за адрес сокета без проверки.
  - Next 16.4.4:
    - `dist/server/lib/start-server.js:204-210`: обработчик запроса ждёт `handlersPromise`, но событие `request` уже испущено;
    - `start-server.js:260, 382`: `getRequestHandlers` вызывается после `listening`;
    - `render-server.js:124` → `next-server.js:573-577`: `register()` выполняется внутри `prepare()`.
- **Доказательство (по коду):** запросы, пришедшие между `listening` и концом `prepare()`, не проходят через `stampPeerAddress`. Присланный клиентом `x-teletau-peer-address` доходит до BFF как есть, и BFF пересылает его в API в `X-Forwarded-For`. Вживую не воспроизводил: собранный веб зашит на API `localhost:4000`, а этот порт мне занимать нельзя.
- **Почему это проблема:** при каждом перезапуске (деплой, падение) можно отправить пачку запросов с разными адресами и обойти лимит по IP. Для QR остаётся лимит на карточку. Для кода класса (30 бит) лимит по IP — основная защита.
- **Предлагаемое исправление:**
  - Ставить отметку вместе с секретом процесса: `peer.ts` генерирует случайный токен в `globalThis` и пишет его во второй служебный заголовок. BFF доверяет адресу только при совпадении токена, иначе IP не передаёт (строже, но не обходится).
  - Либо подключать `peer` через `node --import` в `start` до `listen`.

## Что сделано хорошо (≤ 5 пунктов)
