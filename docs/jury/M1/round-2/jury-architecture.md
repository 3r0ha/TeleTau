## Находки

### [P3] R2-1. Повторная выдача сессии по коду класса не проверяет условия входа: место с отозванным согласием снова получает рабочую сессию
- **Где:**
  - `apps/api/src/modules/identity/student-login.service.ts:113-122` — `poll` проверяет только `account.status`;
  - `apps/api/src/modules/org/join.service.ts:146-147` — ветка `repeat`;
  - для сравнения: `loginWithQr` в том же файле, `:69-70`, проверяет `class_archived` и `consent_revoked`.
- **Доказательство:** скрипт `consent-bypass.mjs` прошёл сценарий: одобрение → первый опрос (сессия S1) → учитель отмечает бумажное согласие → отзывает его. После этого S1 отвечает `401 session_revoked`. Повторный опрос с `X-Device-Install-Id` того же устройства:
  ```
  "consentRevoked": { "firstSessionAfterRevoke": "401 session_revoked",
    "repoll": { "status": "approved", "hasSession": true }, "newSessionMe": 200, "seatConsent": "revoked" }
  "cardReissued":   { "firstSessionAfterReissue": "401 session_revoked", "repoll": { "status": "approved", "hasSession": true } }
  ```
- **Почему это проблема:** по ADR 0016 §5 отзыв согласия блокирует вход места. Исправление M1-07 открыло второй путь входа, который этих проверок не делает. Окно — 15 минут после одобрения. Веб-клиент после получения сессии удаляет заявку (`apps/web/app/student/ticket.ts`, `wait/page.tsx:39-41`), поэтому для обхода нужно намеренно повторить запрос с сохранённым `pollToken` — отсюда P3. Но клиенты M6/M7 будут реализовывать тот же контракт, а сейчас соблюдение запрета держится только на поведении клиента.
- **Предлагаемое исправление:** одна проверка «можно ли войти на это место» (архив класса, отзыв согласия) в org/consent. Её вызывают и `loginWithQr`, и выдача сессии при опросе — первая и повторная. Для повторной выдачи дополнительно отказывать, если после одобрения сессии места были отозваны с причиной `consent_revoked` или `card_reissued`. Тест: «повтор опроса после отзыва согласия → 403 `consent_revoked`».

### [P3] R2-2. Атомарный лимит QR учитывает верные входы, пока они выполняются: 30 настоящих карточек с одного IP одновременно — 9 ответов 429 с `Retry-After: 60`
- **Где:**
  - `apps/api/src/modules/identity/student-login.service.ts:53-66` — попытка резервируется до проверки и возвращается только после `verifyCard`;
  - `apps/api/src/infra/rate-limiter.ts:69-74` — при отказе `Retry-After` равен остатку окна.
- **Доказательство:** скрипт `nat-burst.mjs` берёт карточки из настоящего PDF (декодирует QR) и отправляет параллельные `POST /auth/qr` с одного IP:
  ```
  {"validCards":30,"ms":87,"responses":{"200":25,"429 rate_limited":5}}
  {"validCards":30,"ms":74,"responses":{"200":21,"429 rate_limited retry-after=60":9}}
  {"validCards":40,"ms":75,"responses":{"200":23,"429 rate_limited retry-after=60":17}}
  ```
  В раунде 1 (схема «проверка, потом счёт») верные входы в счётчик не попадали. Это побочный эффект исправления M1-05.
- **Почему это проблема:** весь класс за одним школьным NAT — базовый сценарий (комментарий в `student-login.service.ts:23-24` говорит об этом прямо). При обычной задержке в миллисекунды 21 одновременный запрос маловероятен. Но число выполняющихся запросов растёт вместе с задержкой, то есть в утренний пик, когда API и так медленный. Тогда дети с верными карточками получают блок на 60 с и повторяют вход синхронной волной — это положительная обратная связь. Код класса (лимит 10) устроен так же; в моём прогоне 30 из 30 прошли, то есть там проблема не воспроизвелась.
- **Предлагаемое исправление:** два счётчика в одном Lua-скрипте: неудачи F и резервы P с коротким сроком.
  - Резерв, если `F + P < max`.
  - Успех — `DECR P`; неудача — `DECR P` и `INCR F`.
  - Если отказ только из-за P — `Retry-After: 1`, а не остаток окна.
  - Тест: больше `max` верных параллельных входов с одного IP — все 200.

### [P3] R2-3. `pnpm test` краснеет, если на машине заняты стандартные порты (например, запущен `pnpm dev`)
- **Где:** `scripts/test/dev.test.mjs:43-53` — тест передаёт только `WEB_PORT` и `API_PORT`; `scripts/dev.mjs:75-81,114-116` — остальные приложения берут порты по умолчанию 3100/4100/4200.
- **Доказательство:** мой прогон `pnpm test` под Node 24 завершился с exit 1, пока параллельные жюри держали стек:
  ```
  ✖ findBusyPorts reports an app whose port is already taken (M0-R2-10)
  actual: [ 'web', 'console', 'ai-gateway', 'ml-worker' ], expected: [ 'web' ]
  ```
  После освобождения портов — 24/24.
- **Почему это проблема:** разработчик обычно гоняет тесты при запущенном `pnpm dev`. CI нет (M0-18b), и `verify.sh` — единственный гейт; ложно-красный тест подрывает доверие к нему.
- **Предлагаемое исправление:** в тесте передавать `"0"` для всех ключей: `Object.fromEntries(APP_PORTS.map((p) => [p.key, "0"]))`, а нужный ключ — переопределять.

### [P3] R2-4. Строки `sessions` и `join_requests` не удаляются: по строке на каждое обновление токена, срока хранения нет
- **Где:** `apps/api/src/modules/identity/sessions.service.ts:298` — `mint` вставляет строку при каждой ротации, ротированные строки остаются; `apps/api/src/modules/org/org.schema.ts:182-207` — `join_requests`.
- **Доказательство:** поиск `cleanup|purge|retention|prune|чистк|очистк` по `apps/api/src`, `apps/workers/src`, ADR 0015, docs/07 и `docs/backlog.md` ничего не нашёл.
- **Почему это проблема:** access-токен живёт 15 минут, значит, на каждое устройство приходится строка за каждые 15 минут активной работы. При 100 тыс. активных учеников и 2–4 обновлениях в день это 70–150 млн строк в год с тремя индексами; по этим строкам идут `revokeAccount` и `revokeFamilyRows`. Для обнаружения повтора ротированные строки нужны только до `family_expires_at` (не больше 90 дней). docs/07 обещает секционирование крупных журналов, но `sessions` под это правило не попадает. Заявкам на вход больше суток уже не нужны: страница класса показывает только последние 24 часа.
- **Предлагаемое исправление (Предложение):** задача в workers:
  - удалять строки `sessions`, у которых `family_expires_at < now() - 1 day`, а также отозванные старше N дней;
  - удалять `join_requests` старше 24 часов.

  Либо осознанно перенести в бэклог с целевой вехой (M9/M11).
