## Находки

### [P1] ФИО и должность учителя пишутся в лог API в открытом виде при любой ошибке запроса к БД
- **Где:** `apps/api/src/common/problem.filter.ts:41-43` пишет в лог `exception.stack` для внутренней 500. `DrizzleQueryError` кладёт `params` прямо в текст ошибки (`drizzle-orm/errors.js:12-13`). Фильтр `apps/api/src/common/redact.ts:26-37` по шаблонам маскирует только e-mail и токены. Маскирование по ключу `fullName`/`position` (`redact.ts:58`) работает только для полей объекта, а здесь значения внутри строки. Сопутствующие места:
  - `apps/api/src/common/text.ts:11-14` пропускает U+0000;
  - `apps/api/src/common/logger.ts:27-29` (`printStackTrace(undefined)`) падает с исключением.
- **Доказательство:** изолированный стек `jsec1`, `POST /api/v1/teacher/verification` с `fullName: "Секретова\u0000 Зульфия Рашитовна"`. Ответ — 500, в логе:
  ```
  ERROR [ProblemFilter] Error: Failed query: update "pii"."adult_profiles" set "full_name" = $1, "position" = $2, ...
  params: Секретова  Зульфия Рашитовна,Завуч гимназии 3,…,01a19e94-6c3c-...
  ERROR [ProblemFilter] TypeError: Cannot read properties of undefined (reading 'replace') at redactString ... RedactingLogger.printStackTrace
  ```
  Клиент получает ответ не по RFC 9457: `{"statusCode":500,"error":"Internal Server Error","message":"Cannot read properties of undefined (reading 'replace')"}`. Логгер падает так на любой 500 (видно и на пробах с курсором). Скрипт воспроизведения: `/private/tmp/claude-501/-Users-kitty-Cyber102-Project2/31d359a7-fccf-4e16-be4e-3fb3701df9ee/scratchpad/jsec1/scripts/probe2.mjs`.
- **Почему это проблема:** нарушено непреложное правило 5 CLAUDE.md («никаких ПДн в логах»). NUL — лишь удобный способ воспроизвести. В эксплуатации любой сбой БД (`statement_timeout` 4 с, переключение реплики, взаимоблокировка) во время подачи заявки учителя или отказа модератора выгрузит в лог ФИО, должность и текст причины. Тест `m1-flow.test.ts` «logs (criterion 7)» проверяет только успешный путь.
- **Предлагаемое исправление:**
  - Для `DrizzleQueryError` писать в лог только `e.query`, SQLSTATE и имя ограничения из `e.cause`; `message` и `params` не писать никогда. Либо обрезать всё после `\nparams:` в `redactString`.
  - Чинить `printStackTrace` для `undefined`.
  - В `normalizeTextField` отклонять управляющие символы U+0000–U+001F ответом 422.
  - Добавить тест: принудительная ошибка БД при подаче заявки и перехват логов — в логах нет ФИО.

### [P1] Секрет QR-карточки остаётся в истории браузера: на общем планшете следующий пользователь входит как этот ребёнок
- **Где:** `apps/web/app/q/page.tsx:9-11, 21-22` (комментарий обещает убрать фрагмент «из адресной строки и истории», но вызывается только `history.replaceState`). Ссылка `${PUBLIC_WEB_URL}/q#TT1.<seat>.<secret>.<check>` описана в ADR 0016 §2 и печатается в PDF (`apps/api/src/modules/org/classes.service.ts:277`). Вход по такой ссылке не требует ничего, кроме самой карточки (`apps/api/src/modules/identity/student-login.service.ts:50-77`).
- **Доказательство:** headless Chromium из кеша Playwright с постоянным профилем открыл `http://127.0.0.1:43999/q#TT1.ABCDEFGHJK.0123456789ABCDEFGHJKMNPQRS.6V` с тем же `replaceState`. Адресная строка после этого — `/q`, но в истории профиля полный URL:
  ```
  $ sqlite3 Default/History "select url, visit_count from urls;"
  http://127.0.0.1:43999/q#TT1.ABCDEFGHJK.0123456789ABCDEFGHJKMNPQRS.6V|1
  http://127.0.0.1:43999/q|1
  ```
  Скрипт: `/private/tmp/claude-501/-Users-kitty-Cyber102-Project2/31d359a7-fccf-4e16-be4e-3fb3701df9ee/scratchpad/jsec1/scripts/history.mjs`.
- **Почему это проблема:** ADR 0015 прямо называет основной контекст — «общий школьный планшет». Системная камера iOS и Android открывает ссылку из QR в браузере (демо §4.2: «открыть ссылку из QR напрямую»). Дальше любой одноклассник через историю или подсказку адресной строки входит под этим ребёнком: меняет ник, а с M2–M4 получает доступ к прогрессу и голосам в корпусе. Ребёнок не узнаёт об этом, а перевыпуск карточки незваного гостя не выгоняет (следующая находка). Защита, описанная в ADR, на деле не работает.
- **Предлагаемое исправление:**
  - Класть в QR саму полезную нагрузку `TT1.…` без URL. Её читают сканер веба `/student` и нативные приложения, а системная камера не откроет браузер с секретом.
  - Если ссылка нужна, секрета в ней быть не должно. Компромисс зафиксировать в ADR 0016.
  - Добавить e2e-проверку: после входа в профиле браузера нет `TT1.`.

### [P1] Перевыпуск карточки не завершает сессии, открытые старой карточкой
- **Где:** `apps/api/src/modules/org/classes.service.ts:225-252`. Метод `reissue` отзывает карточку, выпускает новую версию и пишет аудит, но сессии ученика не трогает. Для сравнения, отзыв согласия завершает сессии: `apps/api/src/modules/consent/consent.service.ts:270-272`.
- **Доказательство:** скрипт `/private/tmp/claude-501/-Users-kitty-Cyber102-Project2/31d359a7-fccf-4e16-be4e-3fb3701df9ee/scratchpad/jsec1/scripts/probe5.mjs`:
  ```
  thief QR login                                 200
  teacher reissue seat 1                         200
  old card login now                             card_revoked
  thief access token GET /me after reissue       200
  thief refresh after reissue                    200
  thief GET class after reissue (new token)      200
  ```
- **Почему это проблема:** перевыпуск — единственное действие учителя при утере карточки (демо §6.3, раздел «Защита»). Кто успел войти старой карточкой, сохраняет доступ: ротация продлевает сессию до 90 дней (`sessions.service.ts:24-28`). ASVS L2 требует завершать сессии после отзыва учётных данных. Вместе с предыдущей находкой это значит, что у учителя нет способа выгнать постороннего, кроме отзыва согласия.
- **Предлагаемое исправление:**
  - В транзакции перевыпуска, если место связано с аккаунтом, вызывать `revokeAllSessions(tx, accountId, "card_reissued")`. Новая причина отзыва — аддитивной миграцией, плюс стоп-лист.
  - Добавить в аудит `sessionsRevoked`.
  - Добавить тест в §6.3 `m1-flow`: старая сессия получает 401 `session_revoked`.
  - Предупредить учителя в интерфейсе: «Ученик выйдет на всех устройствах».

### [P2] Лимиты частоты обходятся: гонка «проверил — потом засчитал» и подмена X-Forwarded-For через BFF
- **Где:**
  - `apps/api/src/infra/rate-limiter.ts:33-45`: `assertBelow` читает счётчик, а `hit` увеличивает его отдельным шагом, не атомарно;
  - `apps/api/src/modules/identity/student-login.service.ts:51-63` (QR) и `:81-90` (код класса);
  - `apps/web/src/session/server.ts:65-71`: BFF передаёт X-Forwarded-For клиента как есть;
  - Next 16.4.4 `dist/server/base-server.js:604`: `req.headers['x-forwarded-for'] ??= socket.remoteAddress` сохраняет значение клиента;
  - `.env.example`: `TRUST_PROXY=loopback`;
  - собственный тест `e2e/tests/proxy-ip.spec.ts:19-23, 34-37`: клиент сам задаёт XFF и получает отдельный счётчик.
- **Доказательство:** API на изолированном стеке, запросы с loopback, как их шлёт BFF (`probe3.mjs` и `probe4.mjs` в той же папке scratchpad):
  - 60 параллельных неверных QR с одного IP → `{"401":60}`, 429 нет (лимит 20 в минуту); 200 параллельных → `{"401":49,"429":151}`;
  - 300 параллельных неверных кодов класса с одного IP → `{"404":174,"429":126}` (лимит 10 в минуту);
  - 40 последовательных неверных кодов с меняющимся XFF → `{"404":40}`, ни одного 429; с постоянным XFF → `{"404":10,"429":5}`.
- **Почему это проблема:**
  - Критерий приёмки 5 выполняется только при последовательных запросах.
  - Для QR (130 бит) это не эксплуатируется. Для кода класса (30 бит) перебор с одного IP вырастает в 17 раз, а в dev и демо, где Next доступен напрямую, становится неограниченным.
  - Угаданный код даёт заявку, а поток заявок учителю легко перепутать с настоящими.
  - Ответ 202 раскрывает класс и школу (`ClassCodeLoginTicket.class`), что расходится с `docs/02` §9.
- **Предлагаемое исправление:**
  - Резервировать попытку атомарно до проверки: один Lua-скрипт «INCR, затем сравнение с лимитом».
  - В BFF не передавать X-Forwarded-For клиента: брать адрес сокета либо значение, которое добавил свой балансировщик (настраиваемо).
  - Добавить тест с `Promise.all` на 60 запросов.

### [P2] У веба и консоли нет CSP, HSTS и запрета встраивания в чужие страницы
- **Где:** `apps/web/next.config.ts:3-7` и `apps/console/next.config.ts:3-7` — нет `headers()`, нет `proxy.ts` или `middleware.ts`. Поиск `content-security-policy|x-frame-options|frame-ancestors|strict-transport` по `apps`, `packages` и `infra` ничего не нашёл. При этом `docs/08` §5 требует «CSP без `unsafe-inline`».
- **Почему это проблема:** access-токен лежит в памяти JS (`apps/web/src/session/client.ts:73-81`). Любой XSS — через зависимость или через пользовательский контент M4 — уносит токен учителя или модератора. CSP — задокументированная вторая линия защиты. От кликджекинга сейчас фактически спасает только cookie с `SameSite=Strict`, а не явная политика.
- **Предлагаемое исправление:** `proxy.ts` (Next 16) с CSP на nonce (`script-src 'self' 'nonce-…' 'strict-dynamic'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; connect-src 'self' <API>`), `Permissions-Policy: camera=(self)`, HSTS в production. Добавить e2e-проверку заголовков.

### [P3] Битый курсор пагинации даёт 500 вместо 422
- **Где:** `apps/api/src/common/cursor.ts:12` принимает любую строку или число для любого ключа. Затронуты `apps/api/src/modules/org/directory.service.ts:63`, `apps/api/src/modules/admin/audit.service.ts:84-87`, `apps/api/src/modules/moderation/verification.service.ts:91-93`.
- **Доказательство (`probe1.mjs`):** 500 на каждом из запросов:
  - `GET /schools?cursor=` с base64 от `{"o":"abc"}` и от `{"o":-5}`;
  - `GET /admin/audit-log?cursor=` с `{"at":"x","id":"y"}`;
  - `GET /moderation/teacher-verifications?cursor=` с `{"at":"x","id":"y"}`.

  Каждый такой запрос ещё и роняет логгер (первая находка).
- **Предлагаемое исправление:** проверять курсор по схеме каждого эндпоинта (`o` — целое ≥ 0, `at` — ISO-дата, `id` — UUID) и отвечать 422.

### [P3] Нет блокировки аккаунта сотрудника после неверных TOTP
- **Где:** `apps/api/src/modules/identity/otp.service.ts:52-53, 84-102`.
- **Доказательство (по коду):** 5 попыток на вызов × 5 вызовов на адрес за 10 минут = 25 попыток TOTP за 10 минут с распределённых IP, то есть 3600 в сутки. При окне ±1 шаг верными считаются 3 кода из 10⁶: около 1% успеха в сутки и около 28% за месяц после первого фактора. Пишется только `staff.login_failed`.
- **Предлагаемое исправление:** счётчик неудачных TOTP на аккаунт (например, 10 в час → блокировка на час и запись `staff.locked` в аудит), оповещение.

### [P3] Демо-сотрудники с публичными TOTP-секретами включаются тем же флагом, что и демо-код
- **Где:** `apps/api/src/modules/identity/staff-seed.ts:22-25, 38`; `apps/api/data/README.md`.
- **Почему это проблема:** любая не-production среда с `AUTH_DEMO_OTP` (например, stage для показа заказчику, `docs/08` §1) получает администратора и модератора, у которых второй фактор лежит в репозитории. Через них можно одобрять учителей, читать аудит, ФИО и e-mail заявителей. Демо-код принят владельцем, а отказ от 2FA для сотрудников — нет.
- **Предлагаемое исправление:** отдельный флаг `AUTH_DEMO_STAFF`, запрещённый в production. Секрет — из окружения или генерируется при первом старте и печатается один раз.

### [P3] Причина отказа модератора хранится вне схемы `pii`
- **Где:** `apps/api/src/modules/moderation/verification.service.ts:115-128`, колонка `teacher_verifications.decision_reason` в схеме `public`. Сам код признаёт, что в причине «могут быть ПДн»: поэтому её не пишут в аудит.
- **Предлагаемое исправление:** перенести колонку в `pii` или заменить свободный текст справочником причин и коротким комментарием, который хранится в `pii`.

### [P3] После отзыва согласия данные ребёнка хранятся бессрочно
- **Где:** `apps/api/src/modules/consent/consent.service.ts:245-275`: отзыв закрывает вход и завершает сессии. Аккаунт, ник, членство в классе и `devices` (`install_id`, `last_seen_at`) остаются навсегда. `DELETE /me` отложен (`docs/07` §2: «позже»).
- **Предлагаемое исправление:** записать в бэклог срок хранения и обезличивание аккаунта места после отзыва согласия, например через 30 дней.

## Что сделано хорошо (≤ 5 пунктов)
- **Авторизация идёт от контракта.** `x-access` в `openapi.yaml` проверяется в хуке `onRequest` до разбора тела, страховочный guard не пускает в обработчик без проверки. Матрица `authz-matrix.test.ts` падает, если операция не попала в неё. Всё подтверждено: 118 тестов зелёные на изолированном стеке, IDOR-пробы второго учителя и взрослого дали только 403/404.
- **Минимизация данных детей закреплена в БД.** Триггеры не дают завести строку `pii` для детского аккаунта и превратить взрослого в ребёнка. Ники — из гендерно-нейтрального словаря. QR с фото распознаётся на устройстве. В аудите вместо IP — HMAC.
- **Сессии.** Access-токен ES256 на 15 минут. Refresh-токен — 256 бит, в базе только хеш. Ротация через условный `UPDATE`. Повтор токена отзывает всё семейство, ставит его в стоп-лист Valkey и пишет аудит. Сессия привязана к устройству. Cookie `HttpOnly; SameSite=Strict` ставит BFF, который дополнительно проверяет Origin и Sec-Fetch-Site; обновления в вебе идут строго по одному через `navigator.locks`.
- **Секреты.** Секрет карточки — 130 равномерных бит, в БД только SHA-256. Задания печати лежат в Valkey под AES-256-GCM с AAD 30 минут. У HMAC разделены назначения. В production проверка конфигурации запрещает демо-код, перец по умолчанию и пустые ключи. Ручной поиск ключей и токенов в репозитории ничего не нашёл.
- **Аудит и зависимости.** `audit_log` защищён триггерами и ролью `teletau_app`, и это проверено тестом. `pnpm audit --prod` — 0 уязвимостей. В клиентах нет зарубежных SDK, у Android `allowBackup=false`.

Изолированный стек `jsec1` (порты 45432/46379, API на 44000) и процесс API остановлены, тома удалены. Файлы проекта не менялись.
