## Находки

### [P2] P2-1. Idempotency-Key не атомарен: повтор во время первого запроса выпускает карточки дважды
- **Где:** `apps/api/src/infra/idempotency.ts:18-21` — `get`, затем `fn()`, затем `set NX`. Используется в `apps/api/src/modules/org/classes.service.ts:75` (`createClass`) и `:186` (`issueSeats`).
- **Доказательство:** `scratchpad/jarch/scripts/repro.mjs` против API из `dist` на :34000 отправил два параллельных `POST /classes/{id}/seats` с одним `Idempotency-Key` и `count: 24`. Результат:
  ```
  "idempotencyRace": { "statuses": [201, 201], "printJobs": ["01a19e93-407d-…", "01a19e93-4086-…"], "seatsInClass": 48 }
  ```
  Тест `m1-edges.test.ts:120` проверяет только последовательный повтор.
- **Почему это проблема:** ключ идемпотентности нужен как раз для повтора при плохой связи: клиент повторяет запрос, пока первый ещё выполняется. Вместо 24 мест получается 48, номера 25–48 «висят», а два задания печати содержат разные секреты. Мобильные клиенты (M6/M7) с автоповтором расширят окно гонки. Этот же примитив будут переиспользовать дальше.
- **Предлагаемое исправление:** перед `fn()` ставить маркер `SET idem:… "pending" NX EX 60`. Если маркер уже есть, ждать результат или отвечать 409 `request_in_progress`. Привязать ключ к хешу тела (другое тело — 422). Добавить интеграционный тест на `Promise.all` из двух запросов.

### [P2] P2-2. Сессия по коду класса выдаётся один раз: при потере ответа ученик теряет доступ, место остаётся «осиротевшим»
- **Где:** `apps/api/src/modules/org/join.service.ts:123-141` — `approved → consumed` в той же транзакции, что и выдача сессии; повторный опрос возвращает `consumed` без сессии. `apps/web/app/student/wait/page.tsx:89-91` — «Вход уже выполнен».
- **Доказательство:** `repro.mjs` прошёл одобрение, затем первый опрос (его ответ «потерян»), затем повтор:
  ```
  "poll1": {"status":"approved","hasSession":true}, "poll2": {"status":"consumed","hasSession":false},
  "seatCreatedForStudent": {"number":49,"nickname":"Шустрый компас","cardStatus":"none"}
  ```
- **Почему это проблема:** драйвер «сельские школы со слабой связью» (docs/06 §1). У ученика по коду класса нет карточки, поэтому он не может войти в созданный для него аккаунт. Он подаёт новую заявку, и в классе появляется дубль с другим ником. Восстановиться можно только вручную, если учитель догадается выпустить карточку на место №49.
- **Предлагаемое исправление:** сделать выдачу идемпотентной по `X-Poll-Token` и `deviceInstallId`, пока не истёк срок одобренной заявки. Например, выдавать новое семейство сессии тому же устройству, а предыдущее отзывать. Добавить тест «повтор опроса после approved».

### [P2] P2-3. Потерянный ответ `POST /auth/refresh` разлогинивает и записывает ложный инцидент
- **Где:** `apps/api/src/modules/identity/sessions.service.ts:70` (`if (row.rotatedAt) return this.reuseDetected(…)`); `docs/adr/0015-auth-tokens-and-sessions.md:54,87` («Льготного окна нет… single-flight»).
- **Доказательство:** `repro.mjs`: первый refresh вернул 200 (его ответ «потерян»), повтор с тем же токеном:
  ```
  "refreshLostResponse": {"first":200,"retry":{"status":401,"code":"refresh_reused"},"newAccessTokenAfterRetry":{"status":401,"code":"session_revoked"}}
  ```
- **Почему это проблема:** single-flight защищает от параллельных обновлений, но не от потерянного ответа. В вебе это участок браузер ↔ BFF: потерян `Set-Cookie`. На мобильных — прямой вызов. Access-токен живёт 15 минут, поэтому таких обновлений много. Каждая потеря — выход из аккаунта. Ученик по коду класса теряет доступ к аккаунту (см. P2-2), а модератор видит ложное `session.refresh_reuse_detected`. ADR 0015 при отказе от льготного окна этот сценарий не рассматривал.
- **Предлагаемое исправление:** дополнить ADR 0015. Например: повтор ротированного токена с того же `deviceInstallId` в течение N секунд после ротации, пока преемник ещё не использован, отзывает только преемника и выпускает новую пару без отзыва семейства. В остальных случаях — как сейчас. Добавить тест.

### [P2] P2-4. Один старый refresh-токен пишет в `audit_log` сколько угодно строк; у `/auth/refresh` нет лимита частоты
- **Где:** `apps/api/src/modules/identity/sessions.service.ts:132-146` — аудит пишется при каждом предъявлении ротированного токена, даже когда семейство уже отозвано. `apps/api/src/modules/identity/auth.controller.ts:73-77` — без ограничителя частоты.
- **Доказательство:** `scratchpad/jarch/scripts/audit-amp.mjs` отправил 200 параллельных повторов одного ротированного токена, затем запрос к БД:
  ```
  {"replays":200,"responses":{"401 refresh_reused":200}}
  session.refresh_reuse_detected|200
  ```
- **Почему это проблема:** из `audit_log` нельзя удалять строки (триггеры, ADR 0017), и секционирования до M11 нет. Тот, у кого есть один украденный токен, может засорить журнал со скоростью API: место на диске растёт без ограничений, а настоящий инцидент тонет в шуме. Так же ведёт себя обычный клиент из P2-3, если зациклится на повторе.
- **Предлагаемое исправление:** писать `refresh_reuse_detected` один раз на семейство — только при переходе в `revoked`; повтор по уже отозванному семейству — молча 401. Ограничить `/auth/refresh` по IP и по хешу токена через `RateLimiter.consume`.

### [P2] P2-5. Console зависит от исходников `apps/web/src`, а turbo об этом не знает: самопроверка консоли может быть ложно-зелёной
- **Где:** `apps/console/tsconfig.json:24-31` (`"@teletau/ui": ["../web/src/ui/index.ts"]`, `@teletau/session/*` → `../web/src/session/*`); `apps/console/package.json` — зависимости от web нет; в `turbo.json` нет `inputs`.
- **Доказательство:** `npx turbo run typecheck --filter=@teletau/console --dry=json`: у задачи `@teletau/console#typecheck` (hash `c54614f0dae525f5`) 17 входов, все из `apps/console`. Файлов `apps/web/src` среди них ноль, зависимости — только `@teletau/contracts#build` и `@teletau/design-tokens#build`.
- **Почему это проблема:** если изменение в `apps/web/src/ui` или `src/session` ломает консоль, lint, typecheck, build и test консоли в `verify.sh` достанутся из кеша и будут зелёными. Git и CI пока нет (бэклог M0-18b), так что локальный `verify.sh` — единственный гейт. В M2 консоль получит конструктор курса на этих же компонентах.
- **Предлагаемое исправление:** вынести код в `packages/ui` и `packages/session`, как и планирует docs/06 §5, и объявить их зависимостями обоих приложений. Минимальный вариант — `inputs` для задач console в `turbo.json` с `$TURBO_ROOT$/apps/web/src/**`.

### [P3] Лимиты частоты «сначала проверка, потом счёт» не атомарны
- **Где:** `apps/api/src/infra/rate-limiter.ts:33,42`; `apps/api/src/modules/identity/student-login.service.ts:52-62,82-87,104-116`.
- **Доказательство:** `scratchpad/jarch/scripts/rl-burst.mjs` отправил 100 параллельных неверных `POST /auth/qr` с одного IP: `{"401":56,"429":44}` при лимите 20.
- **Почему это проблема:** под параллельной нагрузкой критерий 5 и ADR 0016 §5 не выполняются: лимит превышен примерно в 2,8 раза. Для 130-битного секрета практического риска нет, для 30-битного кода класса запас меньше.
- **Предлагаемое исправление:** атомарно резервировать попытку через Lua «INCR и проверка» и возвращать её (`DECR`) при успехе; либо проверять и считать в одном скрипте.

### [P3] Вызовы BFF → API и браузер → API без таймаута (расходится с docs/06 §6.8)
- **Где:** `apps/web/src/session/server.ts:70` (`fetch(r, { cache: "no-store" })` без `signal`); `apps/web/src/session/api.ts:18`; `apps/web/src/session/react.ts:78-87` — следующий опрос ставится только после завершения текущего.
- **Почему это проблема:** «зависшее» TCP-соединение — частое явление в мобильных сетях — держит обработчик Next до таймаутов undici по умолчанию (около 300 с). Опрос страницы класса раз в 3 с встаёт, и учитель не видит новых учеников, хотя индикатора офлайна нет.
- **Предлагаемое исправление:** `AbortSignal.timeout(…)` в BFF и в `authFetch`; добавить строку про BFF в таблицу §6.8.

### [P3] PDF карточек рендерится в event loop API
- **Где:** `apps/api/src/modules/org/classes.service.ts:274` (`renderCardsPdf` в обработчике запроса).
- **Доказательство:** `scratchpad/jarch/scripts/pdf-bench.mjs`: PDF на 40 карточек — 842–966 мс (347 КБ). Пять параллельных — 3874 мс по стенным часам, то есть фактически последовательно. Задержка `/health` во время рендера — 22–151 мс против 2 мс в простое.
- **Почему это проблема:** если в начале учебного года несколько учителей печатают одновременно, рендер на одном процессе выстраивается в очередь, и страдают соседние запросы.
- **Предлагаемое исправление (Предложение):** вынести рендер в пул `worker_threads` или в очередь workers (BullMQ) — с учётом того, что ADR 0018 хранит секреты только в задании печати.

### [P3] Нестабильный юнит-тест PDF под нагрузкой
- **Где:** `apps/api/test/cards-pdf.test.ts:7` — таймаут по умолчанию 5 с.
- **Доказательство:** `turbo run … --force` при нагрузке около 11,5: «Error: Test timed out in 5000ms». Отдельные прогоны — 1,1–3,4 с; полный юнит-прогон при нагрузке около 3 — 73/73 зелёные.
- **Предлагаемое исправление:** явный таймаут, например 20 с; тяжёлый разбор PDF через pdfjs и jsqr оставить в интеграционном проекте.

### [P3] При пустом справочнике документов принятие условий считается выполненным
- **Где:** `apps/api/src/modules/consent/consent.service.ts:62-67` — ошибка сида только пишется в лог; `:131` — `if (current.length === 0) return []`. Через `hasAcceptedRequired` это попадает в `verification.service.ts` (`submit`).
- **Почему это проблема:** если на свежей базе сид упал при старте (база ещё не готова), повтора нет, а взрослые подают заявку учителя без принятых условий.
- **Предлагаемое исправление:** при пустом справочнике отвечать 503 или 409 `documents_unavailable`; сид — отдельной командой или миграцией с повтором.

### [P3] Мелочи в данных
- Триграммные GIN-индексы `schools_name_ru_trgm_idx` и `schools_short_name_ru_trgm_idx` (`org.schema.ts:61-62`) построены по сырым столбцам, а запрос сравнивает `translate(lower(...))` (`directory.service.ts:37,71`). `EXPLAIN` даже при `enable_seqscan=off` показывает Seq Scan. На 1694 школах это неважно, но индексы мёртвые: нужен индекс по выражению или их удаление.
- В `verification.service.ts:164` при отсутствии школы в ответ контракта подставляется `districtId: r.schoolId` — неверные данные; лучше 500 или явное отсутствие поля.
