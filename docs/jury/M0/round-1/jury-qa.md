## Находки

### [P1] API падает при перезапуске или обрыве соединения Postgres вместо ответа 503
- Где: `apps/api/src/infra/infra.module.ts:14` — `new pg.Pool(...)` без обработчика `'error'`; на `:20` у ioredis тоже нет обработчика.
- Доказательство: запуск на изолированной копии (compose-проект `teletauqa`, порты 25432/26379), 3 прогона из 3:
  ```
  cd apps/api && API_PORT=14005 DATABASE_URL=... VALKEY_URL=... node dist/main.js &
  curl localhost:14005/api/v1/health      # 200
  docker compose restart postgres          # в течение 10 с после запроса
  curl localhost:14005/api/v1/health      # 000 (connection refused)
  run 1..3: before=200 after-restart=000 EXIT=1
  ```
  Фрагмент лога:
  ```
  throw er; // Unhandled 'error' event
  Emitted 'error' event on BoundPool instance at:
  error: terminating connection due to administrator command   (severity FATAL, code 57P01)
  ```
  Под `pnpm dev` после этого API не поднимается сам: `Failed running 'dist/main.js'. Waiting for file changes before restarting...`.
- Почему это проблема:
  - План T6 требует «503 при отказе». Health нужен именно для того, чтобы сообщать об отказе зависимости, а здесь он умирает вместе с процессом.
  - Падение вызывает любое закрытие простаивающего соединения: рестарт или failover управляемой БД, `pg_terminate_backend`, обрыв сети. При живом трафике в пуле всегда есть простаивающие соединения, так что все инстансы API упадут одновременно.
  - `InfraModule` — общий поставщик пула для всех будущих модулей, дефект унаследуют все.
  - Тесты этого не ловят: unit-тесты работают на фейках (`test/fakes.ts`), интеграционные не обрывают соединения.
  - Остальные сценарии в порядке: остановка Valkey даёт 503 и затем 200; «зависший» Postgres (`docker compose pause`) даёт 503 примерно за 1,0 с при 15 параллельных запросах; старт без доступных зависимостей даёт 503.
- Предлагаемое исправление:
  - `pool.on("error", e => logger.warn(...))` и `redis.on("error", ...)` в фабриках (заодно пропадёт спам `[ioredis] Unhandled error event` в логе).
  - Интеграционный тест: запрос к health → `SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE usename='teletau' AND pid<>pg_backend_pid()` → процесс жив, следующий запрос возвращает 200.

### [P2] `normalize` / `toComparable` / `fold` в TS бросают `RangeError` на длинном тексте; Swift и Kotlin его обрабатывают
- Где: `packages/bashkir-text/src/normalize.ts:87` и `:108` — `String.fromCodePoint(...cps)`.
- Доказательство:
  ```
  node -e 'import(".../bashkir-text/dist/index.js").then(m=>m.normalize("ә".repeat(130000)))'
  → RangeError: Maximum call stack size exceeded
  ```
  Бинарный поиск порога: падение начинается с ~125 021 кодовой точки (~244 КБ UTF-8). Реалистичный текст из 168 000 символов тоже падает. Swift и Kotlin на 500 000 кодовых точек отрабатывают без ошибок.
- Почему это проблема:
  - Платформы ведут себя по-разному, а `bashkir-text` должен вести себя одинаково везде.
  - На сервере это даст 500 на длинном вводе: лимит тела Fastify 1 МБ пропускает ~500 тыс. кириллических символов.
  - В M4 это может уронить воркер импорта корпуса.
- Предлагаемое исправление: собирать строку частями (например, по 8192 кодовые точки) или через `map(...).join("")`; добавить во все три порта тест на вход длиной 200 000.

### [P2] Проверка границ модулей молча проходит, если в пути к репозиторию есть пробел или не-ASCII символы
- Где: `apps/api/scripts/boundaries.mjs:71-72` — сравнение ``import.meta.url === `file://${process.argv[1]}` ``. URL закодирован percent-кодировкой, `argv` — нет, поэтому код проверки вообще не выполняется.
- Доказательство: одно и то же нарушение (`health.service.ts` → `../other/some.js`) в трёх каталогах:
  ```
  [plainpath]     → «Нарушены границы модулей (1)…» exit=1
  [проект кәрәҙ] → (пусто) exit=0
  [with space]    → (пусто) exit=0
  ```
- Почему это проблема: непреложное правило 4 молча отключается локально у разработчиков с кириллицей в пути (например, `~/Проекты/…`) — вероятный случай для команды из РБ. В CI путь ASCII, поэтому там проверка работает.
- Предлагаемое исправление: `import.meta.url === pathToFileURL(process.argv[1]).href` и `fileURLToPath(import.meta.url)`, как уже сделано в остальных скриптах.

### [P3] Часть ошибок API приходит не в формате RFC 9457
- Где: `apps/api/src/bootstrap.ts:18` — `new FastifyAdapter()` без `frameworkErrors`.
- Доказательство: `GET /api/v1/%E0%A4%A` → `400 application/json {"statusCode":400,"code":"FST_ERR_BAD_URL",...}`. В контракте для `default` указан `application/problem+json`. Остальные ошибки отдаются корректно в формате problem+json: 404 на неизвестный маршрут или метод, 400 на битый JSON, 413 на тело 2 МБ.
- Предлагаемое исправление: `new FastifyAdapter({ frameworkErrors: (err, req, reply) => …problem })` и e2e-тест на этот случай.

### [P3] bashkir-text: дыры в векторах и зависимость регистра от версии Unicode

- Дифференциальный фаззинг: 40 000 строк плюс полный перебор всех кодовых точек, отдельно и после «а».
  - Реалистичный набор: 0 расхождений TS, Swift и Kotlin.

- Предлагаемое исправление: генерировать набор векторов «по таблице» прямо из `bashkir-homoglyphs.json`; зафиксировать перевод в нижний регистр собственной таблицей для кириллицы, латиницы и греческого.

### [P3] Текстовые краевые случаи (на заметку для jury-language-ai)
