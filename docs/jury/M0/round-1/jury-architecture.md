## Находки

### [P1] API падает при обрыве соединения с Postgres вместо ответа 503
- Где: `apps/api/src/infra/infra.module.ts:13-14` — `pg.Pool` создаётся без обработчика `error`; `scripts/run-ts-app.mjs:15` — `node --watch` не перезапускает процесс после падения.
- Доказательство: поднял API на :4901 с `DATABASE_URL=...?application_name=jury_arch_probe`, `GET /api/v1/health` вернул 200. Затем выполнил `SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE application_name='jury_arch_probe'`. Postgres шлёт этот же FATAL 57P01 всем клиентам при `docker compose stop postgres`, рестарте или failover. В логе:
  ```
  node:events:505  throw er; // Unhandled 'error' event
  error: terminating connection due to administrator command
  Emitted 'error' event on BoundPool instance at: Client.idleListener (pg-pool/index.js:62)
  api exited with code 1
  ```
  `node --watch` после падения пишет `Failed running '...'. Waiting for file changes before restarting...`, то есть в `pnpm dev` API сам не поднимется. Для сравнения: при недоступном Valkey API отвечает `503 {"checks":{"postgres":"ok","valkey":"down"}}` и продолжает работать.
- Почему это проблема: требование T6 «503 при отказе» для Postgres не выполняется, процесс падает. Падение происходит, если в пуле есть простаивающее соединение: 10 с после любого запроса, а под нагрузкой и с health-пробами — всегда. При failover управляемой БД упадут все поды API одновременно. Демо проверяет только Valkey, e2e-тест работает на фейках, интеграционный тест отказ не моделирует, поэтому дефект не виден.
- Предлагаемое исправление: в фабрике `PG_POOL` добавить `pool.on("error", …)` с логированием без ПДн. Добавить интеграционный тест: оборвать своё соединение через `pg_terminate_backend`, затем проверить, что процесс жив и следующий health отвечает 200 или 503. В `docs/demo/M0.md` добавить шаг с остановкой Postgres.

### [P2] Правило «модуль не читает чужие таблицы» автоматически не проверяется
- Где: `apps/api/scripts/boundaries.mjs:28-39`; `apps/api/drizzle.config.ts:5` — одна общая схема `src/db/schema.ts`; `apps/api/src/infra/infra.module.ts:7` — `@Global()` отдаёт `PG_POOL` любому модулю. Обещание проверки — в `CLAUDE.md:19` и `docs/06-architecture.md:97`.
- Доказательство: вызвал `findViolations` из скрипта на четырёх сценариях, все вернули `[]`:
  - (A) `progress` импортирует `accounts` из `../../db/schema.js`;
  - (B) внутренности `identity` реэкспортированы через `src/common/reexport.ts`;
  - (C) таблица экспортирована через `identity/index.ts`;
  - (D) сырой SQL `SELECT * FROM accounts`.
- Почему это проблема: с M1 появятся таблицы. Общий `schema.ts` вместе с глобальным пулом позволит любому модулю читать любую таблицу, и CI останется зелёным. Выделить `consensus` или `realtime` в отдельный сервис (ADR 0001) станет дорого. Сейчас это исправляется почти бесплатно, после M1 — уже нет.
- Предлагаемое исправление:
  - схему Drizzle разложить по модулям (`src/modules/<m>/<m>.schema.ts`), в drizzle.config указать glob;
  - в `boundaries.mjs` разрешить импорт `*.schema.ts` и репозиториев только внутри своего модуля и запретить их реэкспорт из `index.ts`;
  - запретить импорт `src/modules/**` из `src/common`, `src/db`, `src/config`, как это уже сделано для `infra`.

  Предложение (оформить новым ADR): отдельная схема Postgres и роль на каждый модуль, чтобы была защита и в рантайме.

### [P2] `normalize` не идемпотентна и может вернуть строку не в NFC; ошибка в самом алгоритме контракта
- Где: `contracts/shared/bashkir-homoglyphs.json:6-7` — NFC выполняется до удаления невидимых символов. Все три порта повторяют этот порядок: `packages/bashkir-text/src/normalize.ts:83`, `ios/Packages/TeleTauCore/Sources/BashkirText/BashkirText.swift:17-18`, `android/core/bashkirtext/src/main/kotlin/ru/teletau/core/bashkirtext/BashkirText.kt:21-23`.
- Доказательство:
  ```
  е+ZWSP+U+0308          once: U+0435 U+0308       twice: U+0451       NOT IDEMPOTENT isNFC: false
  и+SHY+U+0306           once: U+0438 U+0306       twice: U+0439       NOT IDEMPOTENT isNFC: false
  к+лат.o+ZWJ+U+0308     once: U+043A U+043E U+0308  twice: U+043A U+04E9 (ө)  NOT IDEMPOTENT
  ```
  Идемпотентность проверяется только на входах векторов: `packages/bashkir-text/test/vectors.test.ts:50-59`, Swift `BashkirTextTests.swift:111-118`, Kotlin `BashkirTextVectorsTest.kt:111-119`. Фаззер, который упоминается в `contracts/test-vectors/README.md`, в репозитории отсутствует.
- Почему это проблема: нормализованная форма будет ключом для сравнения ответов, дедупликации вариантов корпуса и индексов (M2, M4). У одного и того же текста получается две «канонические» формы, а вставленный ZWJ позволяет обойти дедупликацию. Когда нормализованные колонки окажутся в БД, исправление потребует миграции данных.
- Предлагаемое исправление: в алгоритме контракта повторять NFC после шагов 2–5 (или удалять невидимые символы до NFC). Выпустить `normalize` v2 с векторами на эти случаи во всех трёх портах. Добавить property-тест (fast-check): `normalize(normalize(x)) === normalize(x)` и результат в NFC, на случайных строках из кириллицы, комбинирующих знаков и невидимых символов. Положить дифференциальный фаззер в репозиторий.

### [P2] workers теряют пароль, TLS и номер БД из `VALKEY_URL`
- Где: `apps/workers/src/config.ts:12-13`; тест `apps/workers/test/system.test.ts:14-17` закрепляет урезанный формат.
- Доказательство:
  ```
  rediss://:s3cret@valkey.prod.internal:6380/2 => {"connection":{"host":"valkey.prod.internal","port":6380}}
  ```
- Почему это проблема: API передаёт URL в ioredis целиком (`infra.module.ts:20`), а workers — только хост и порт. В любом окружении с паролем или TLS (управляемый Valkey) workers получат NOAUTH или уйдут в БД 0 без шифрования. Получается, что два приложения одного стенда читают одну переменную по-разному.
- Предлагаемое исправление: передавать в BullMQ `connection: new Redis(url, { maxRetriesPerRequest: null })` или разбирать username, password, db и tls. Вынести общий модуль конфигурации Valkey. Добавить тест на `rediss://` с паролем.

### [P2] Схемы ответов с `additionalProperties: false` противоречат правилу «поля только добавляются», и CI этого не ловит
- Где: `packages/contracts/openapi.yaml:53`, `:66`; правило — `docs/07-data-and-api.md:181`; `docs/adr/0002-contract-first-openapi.md:12` называет Health образцом.
- Доказательство: в копию спецификации добавил обязательное поле `checks.clickhouse` и запустил `docker run … tufin/oasdiff:v1.35.0 breaking base.yaml next2.yaml --fail-on ERR`. Результат: `No breaking changes to report`, exit 0; в changelog это `info [response-required-property-added]`. Для сравнения, новое значение enum oasdiff ловит (2 error, exit 1) — это хорошо.
- Почему это проблема: swift-openapi-generator (по ADR 0002 подключается с M1) для схем с `additionalProperties: false` генерирует строгий декодер, который отвергает неизвестные ключи (`ensureNoAdditionalProperties`). Это поведение генератора я знаю по его документации, сам в этом прогоне не проверял — Swift-клиент ещё не генерируется. Приложение из стора, собранное по текущему контракту, перестанет разбирать ответ, как только сервер добавит поле. При этом правило обещает поддержку двух мажорных версий приложения. Health — образец, который будут копировать.
- Предлагаемое исправление: убрать `additionalProperties: false` из схем ответов и оставить только для тел запросов. Добавить правило Redocly, которое запрещает это свойство в схемах, достижимых из `responses`. Для перечислений, которые будут расти, использовать `x-extensible-enum`. Предложение: дополнительно сравнивать спецификацию с версией в main, а не только с `openapi.baseline.yaml`, который можно поменять в том же PR.

### [P3] `boundaries.mjs` молча ничего не проверяет, если в пути к репозиторию есть пробел или кириллица
- Где: `apps/api/scripts/boundaries.mjs:71-72`.
- Доказательство: тот же скрипт с тем же нарушением в каталоге `…/scratchpad/Мой проект/apps/api` завершается с `exit=0` и ничего не печатает. В ASCII-пути выдаёт `Нарушены границы модулей (1) … exit=1`.
- Почему это проблема: `import.meta.url` закодирован процентами, а `process.argv[1]` — нет, поэтому сравнение не срабатывает. У разработчика с путём вроде `~/Проекты/…` локальный `verify.sh` будет зелёным при нарушении. CI это ловит, потому что путь там ASCII.
- Предлагаемое исправление: `fileURLToPath(import.meta.url) === resolve(process.argv[1])` и `fileURLToPath` вместо `.pathname`.

### [P3] При недоступном Valkey лог заваливает трассировками
- Где: `apps/workers/src/main.ts:6-10` — нет `worker.on("error")` и `queue.on("error")`; `apps/api/src/infra/infra.module.ts:20` — у ioredis нет обработчика `error`.
- Доказательство: поднял временный Valkey на :26399 и остановил его. За ~10 с workers записали 677 строк лога (144 трассировки ECONNREFUSED); после возврата Valkey воркер переподключился, это хорошо. API за 8 с выдал 8 сообщений `[ioredis] Unhandled error event`.

- Предлагаемое исправление: обработчики `error` с троттлингом и структурным логом.
