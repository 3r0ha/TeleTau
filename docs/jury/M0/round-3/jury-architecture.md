## Находки

### [P2] Тесты `bashkir-text` с абсолютными порогами по времени падают при загруженном процессоре, в том числе шаг CI `pnpm test`
- **Где:**
  - `/Users/kitty/Cyber102/Project2/packages/bashkir-text/test/vectors.test.ts:81-117`. У теста «200 000 кодовых точек» (стр. 83) действует таймаут vitest по умолчанию — 5 с. Остальные тесты сравнивают время с жёсткими порогами: `toBeLessThan(1000)` и `toBeLessThan(1500)` (стр. 116).
  - `/Users/kitty/Cyber102/Project2/ios/Packages/TeleTauCore/Tests/BashkirTextTests/BashkirTextTests.swift:210,214` — порог 3 с.
- **Доказательство (всё на Node 24.22.2):**
  - **Без нагрузки** (`vitest run` в пакете, 3 прогона) — зелёный. Время тестов: 200 тыс. кодовых точек — 1336–1762 мс при таймауте 5 с; цепочка ZWJ между эмодзи — 452–695 мс при пороге 1500 мс. Запас всего в 2–3 раза.
  - **`turbo run lint typecheck test build --force`** — 3 прогона из 3 красные. В раунде 2 эта же команда была зелёной, 44 из 44.
    ```
    × normalize, toComparable and fold do not overflow the stack 6429ms / 8158ms / 6781ms
      Error: Test timed out in 5000ms.
    × a long ZWJ chain between emoji is kept; toComparable and fold stay fast
      AssertionError: expected 2619.19 / 4853.99 / 2152.53 to be less than 1500
    × 200 000 ZWJ without letter neighbours are kept, under 1 s
      AssertionError: expected 1149.17 to be less than 1000
    ```
  - **Шаг CI `turbo run test --force`:**
    - без посторонней нагрузки — 3 из 3 зелёные;
    - 4 из 8 ядер заняты циклами — 2 из 2 зелёные;
    - **6 из 8 ядер заняты циклами — 2 из 2 красные** (`overflow the stack 5675ms / 6022ms — Test timed out in 5000ms`).

    Нагрузка с двумя свободными ядрами — оценка снизу для двухъядерного раннера GitHub (`ubuntu-24.04` для приватных репозиториев). Там ядра медленнее, чем у Apple M-серии, и их честно только два.
  - **Swift:** в моём прогоне `verify.sh` 200 тыс. ZWJ обработались за 831 мс. Жюри QA до паузы видело 1,5–2,8 с при пороге 3 с.
  - **Kotlin:** 39 мс при пороге 1000 мс — запас достаточный.
- **Почему это проблема:**
  - Тесты появились в этом раунде вместе с исправлением M0-R2-03. Они проверяют не поведение, а скорость конкретной машины в конкретный момент.
  - CI запускает `pnpm test` с параллельными задачами turbo. На двухъядерном раннере красный CI ожидаем без всякого дефекта в коде, а это гейт 5 и задача T11.
  - Такие тесты быстро приучают команду «перезапускать до зелёного».
  - Кроме того, тест «200 000 кодовых точек» по смыслу проверяет отсутствие переполнения стека, а падает по таймауту.
- **Предлагаемое исправление:**
  - Тесту на 200 тыс. кодовых точек задать явный щедрый таймаут, например 30 с: его цель — стек, а не скорость.
  - Линейность проверять отношением, а не абсолютным временем: медиана t(4n)/t(n) по 3–5 замерам меньше 8. Для линейного алгоритма отношение около 4, для квадратичного около 16, и оно не зависит от равномерного замедления. То же сделать в Swift и Kotlin.
  - Либо вынести замеры в отдельный шаг `test:perf`, который запускается последовательно после остальных тестов в `verify.sh` и в CI.

### [P3] Нижняя граница `VALKEY_WORKER_SOCKET_TIMEOUT_MS` (6 с) меньше окна блокировки BullMQ при отложенных задачах (до 10 с)
- **Где:**
  - `/Users/kitty/Cyber102/Project2/apps/workers/src/config.ts:8` — `.min(6000)`.
  - `/Users/kitty/Cyber102/Project2/docs/06-architecture.md:203` — обоснование «окно `drainDelay` — 5 с».
- **Доказательство:**
  - В BullMQ 6.5.3 (`node_modules/bullmq/dist/esm/classes/worker.js:16,490`) при наличии отложенных задач воркер блокируется на `Math.min(blockDelay / 1000, this.maximumBlockTimeout)`, где `defaultMaximumBlockTimeout = 10`.
  - Эксперимент: `createSystemQueue` из `dist`, Valkey db 15, одна задача с `delay: 60_000`, наблюдение 25 с.
    ```
    socketTimeout=7000 ms (config accepted), errors in 25 s: 2 ["valkey/worker: Socket timeout. Expecting data, but didn't receive any in 7000ms.", …]
    socketTimeout=15000 ms (config accepted), errors in 25 s: 0
    ```
- **Почему это проблема:**
  - Конфигурация принимает значения от 6 до 10 с, а с ними штатное ожидание задач рвётся каждые несколько секунд. Начнутся переподключения и предупреждения в логе.
  - Отложенные задачи — напоминания и уведомления — появятся с M1–M3.
  - Значение по умолчанию (15 с) безопасно, поэтому серьёзность P3.
- **Предлагаемое исправление:**
  - Поднять минимум до 11–12 с.
  - В §6.8 указать оба окна: `drainDelay` (5 с) и `maximumBlockTimeout` (10 с).
  - Если `drainDelay` когда-нибудь станет настраиваемым, проверять при старте `socketTimeout > max(drainDelay, 10 с) + запас`.

### [P3] Таймаут пула Postgres для обычных запросов не проверяется поведенческим тестом, а health не пишет в лог причину `down`
- **Где:**
  - `/Users/kitty/Cyber102/Project2/docs/06-architecture.md:206` — фраза «без таймаутов — не возвращается вовсе».
  - `/Users/kitty/Cyber102/Project2/apps/api/src/modules/health/health.service.ts:38-40` — `catch { return "down"; }` без записи в лог.
- **Доказательство:**
  - Мутация через окружение: `DB_QUERY_TIMEOUT_MS=600000 DB_STATEMENT_TIMEOUT_MS=599000 pnpm --filter @teletau/api test:integration` даёт `Tests 7 passed (7)`. Тест с «чёрной дырой» для Postgres проходит и с десятиминутным таймаутом пула: health использует собственный `query_timeout`.
  - Для сравнения, мутация `VALKEY_SOCKET_TIMEOUT_MS=600000` честно роняет тест: `× recovers within 5 s after a valkey black hole heals`.
  - Мой отдельный прогон пула из `dist` через прокси «чёрная дыра», 10 обычных `pool.query("SELECT 1")`:
    ```
    default: during partition: 5 s ['Query read timeout'];  after heal: ok 0 s
    mutant : during partition: 12 s ['still hanging after 12 s'];  after heal → Error: timeout exceeded when trying to connect
    ```
    Политика работает и защищает ровно то, что важно с M1, но фиксирует её только юнит-тест значений конфигурации (`clients.test.ts`).
  - Лог интеграционного прогона: во время разрыва с Valkey есть `WARN valkey: Socket timeout…`, а во время разрыва с Postgres нет ни одной строки.
- **Почему это проблема:**
  - Документ утверждает, что поведение проверено, но для пользовательских запросов это неправда.
  - При разрыве с Postgres оператор видит только 503, причину в логе он не узнает.
- **Предлагаемое исправление:**
  - Добавить в `resilience.test.ts` сценарий: обычный `pool.query` через прокси завершается ошибкой не позже `DB_QUERY_TIMEOUT_MS + 1 с`, а после восстановления сети новый запрос проходит.
  - В health передавать ошибку пробы в `reportInfraError`: там уже есть ограничение частоты, поэтому шквала строк не будет.
  - Уточнить формулировку в §6.8.

### [P3] Проверка владения таблицами: остаточные обходы, а ADR 0014 описывает только правила 1–3
- **Где:**
  - `/Users/kitty/Cyber102/Project2/apps/api/scripts/boundaries.mjs:21` — `DRIZZLE_DECL_RE` содержит закрытый список функций.
  - `/Users/kitty/Cyber102/Project2/docs/adr/0014-module-table-ownership.md:12` — «Правила 1–3 проверяет…», хотя в скрипте их уже шесть.
- **Доказательство:** прогнал `findViolations` на сценариях (`$TMPDIR/bnd/probe*.mjs`).
  ```
  A export* через сервис / B pgTable в tables.ts / C import * as ns; export {ns} / E многострочный export  => пойманы
  L pgTableCreator(...)                                    => [] (NOT CAUGHT)
  H import { pgTable as table } … table("accounts")        => [] (NOT CAUGHT)
  D import { accounts }; export const identityTables = { accounts } => [] (NOT CAUGHT)
  J export default schema; index: export { default as tables }      => [] (NOT CAUGHT)
  ```
- **Почему это проблема:**
  - `pgTableCreator` — документированный способ объявлять таблицы в Drizzle, и это тот же класс обхода, что закрывался в M0-R2-04.
  - Остальные сценарии — намеренный обход, а регулярным выражением всех не поймать.
  - Сырой SQL ADR честно относит к защите во время выполнения, это не дефект.
- **Предлагаемое исправление:**
  - Добавить `pgTableCreator` в список.
  - Предложение: перевести правило 4 на проверку через компилятор TypeScript (`ts.TypeChecker`): ни один экспорт `index.ts` модуля не имеет типа `PgTable` или `PgSchema` и не содержит их. Это закрывает импорт под другим именем, обёртку в объект и `default` разом.
  - Обновить п. 4 в ADR 0014.
