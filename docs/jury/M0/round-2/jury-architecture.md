## Находки

### [P2] Нет таймаутов на запросы к Postgres и Valkey: после сетевого разрыва API остаётся в 503 до таймаута TCP в ОС и ничего не пишет в лог
- Где:
  - `apps/api/src/infra/clients.ts:17` — у `pg.Pool` задан только `connectionTimeoutMillis`, нет `query_timeout` и `keepAlive`.
  - `apps/api/src/infra/clients.ts:24` — у ioredis нет `socketTimeout` и `commandTimeout`.
  - `apps/api/src/modules/health/health.service.ts:8-22,43` — `withTimeout` отдаёт ответ «down», но запрос продолжает занимать клиента пула.
  - `grep -rn "query_timeout\|statement_timeout\|keepAlive\|socketTimeout\|commandTimeout" apps/api/src apps/workers/src packages/runtime/src` ничего не находит.
- Доказательство: TCP-прокси имитирует разрыв. В режиме «чёрная дыра» существующие соединения перестают получать данные. После «лечения» новые соединения проходят, а старые остаются мёртвыми, как при падении узла без RST. API запускался из `dist` на :4911.
  - **Postgres.** Прогрев: 60 параллельных health, в базе 10 соединений. Затем разрыв и 20 параллельных запросов, все 503. После лечения прямой `psql` к базе отвечает `ok`, но API 30 проб подряд за 60 с отвечает `503 {"checks":{"postgres":"down","valkey":"ok"}}`. В логе 0 строк WARN.
  - **Valkey.** После лечения `valkey-cli ping` возвращает `PONG`, а API 20 проб за 60 с отвечает `503 … "valkey":"down"`. В логе тоже 0 WARN.
  - **Контроль.** Тот же сценарий с настройками pg `query_timeout: 1500, keepAlive: true` и ioredis `socketTimeout: 3000`: оба клиента восстанавливаются через 0–2 с после лечения.
- Почему это проблема:
  - Failover управляемой БД или Valkey с переездом узла, падение ВМ или разрыв сети между зонами оставляют соединения без RST. Такие соединения висят до таймаута повторной передачи TCP: в Linux по умолчанию около 15 минут (`tcp_retries2=15`).
  - Пул из 10 клиентов исчерпывается запросами, которые были в полёте в момент сбоя. С M1 это будут уже не health-пробы, а все запросы пользователей.
  - Readiness-проба по этому эндпоинту выведет из балансировки все поды на всё это время.
  - Демо (`docs/demo/M0.md:32`) называет `docker compose restart postgres` равнозначным failover. Но рестарт присылает клиентам FATAL 57P01 и закрывает соединения, поэтому этот режим отказа ни демо, ни тесты не проверяют.
- Предлагаемое исправление:
  - В `createPgPool` задать `query_timeout` (больше серверного `statement_timeout` с запасом), `statement_timeout` и `keepAlive: true`. При таймауте `pool.query` возвращает клиента с ошибкой, и пул его уничтожает.
  - В `createValkey` и в подключении BullMQ задать `socketTimeout` (ioredis 6.0.0 его поддерживает) и/или `commandTimeout`.
  - Записать политику таймаутов для внешних вызовов в сквозные решения `docs/06-architecture.md`.
  - Добавить интеграционный тест с TCP-прокси «чёрная дыра» для Postgres и Valkey.

### [P3] Проверку владения таблицами можно обойти транзитивным реэкспортом или таблицей вне `*.schema.ts`
- Где:
  - `apps/api/scripts/boundaries.mjs:33` — схема определяется только по имени файла.
  - `apps/api/scripts/boundaries.mjs:52` — ловится только прямой импорт схемы в `index.ts`.
- Доказательство: прогнал `findViolations` на трёх сценариях:
  ```
  A transitive re-export of schema via service => []
  B pgTable in non-schema file exported from index => []
  D export * from schema in index => ["…index.ts реэкспортирует схему модуля «identity»…"]
  ```
  - (A) `index.ts` делает `export * from "./identity.service.js"`, а сервис реэкспортирует `accounts` из `identity.schema.ts`.
  - (B) `pgTable` объявлена в `tables.ts`. `identity.schema.ts` реэкспортирует её, поэтому drizzle-kit таблицу найдёт, а `index.ts` экспортирует `tables.js`.
- Почему это проблема: ADR 0014 (п. 2 и 4) обещает, что таблицы не выходят за пределы модуля и это проверяется. А barrel-файлы с `export *` в NestJS-модулях — обычная практика. Если в модуле `progress` объявить `pgTable("accounts")` над чужой таблицей, это фактически сырой SQL. ADR честно относит такой случай к защите в рантайме, это не дефект.
- Предлагаемое исправление: проверять транзитивное замыкание экспортов `index.ts`, то есть цепочки `export *` и `export {…} from`. Запретить `pgTable(`, `pgSchema(` и `pgEnum(` вне `*.schema.ts`. Добавить тесты на оба сценария.

### [P3] Два разборщика `VALKEY_URL`: workers не подключаются по IPv6-адресу и игнорируют параметры URL
- Где: `packages/runtime/src/valkey.ts:26` — `host: url.hostname`. Комментарий в строке 14 утверждает «все приложения читают одну переменную одинаково». Но API (`apps/api/src/infra/clients.ts:24`) отдаёт URL на разбор ioredis.
- Доказательство:
  ```
  redis://[::1]:16379   runtime: {"host":"[::1]",…}   ioredis: {"host":"::1",…}
  redis://h:6379/0?family=6   runtime: без family   ioredis: "family":6
  runtime-parsed [::1] connect: Connection is closed.
  ioredis-parsed [::1] connect: ok PONG
  ```
- Почему это проблема: корень M0-06 остался — одну переменную по-прежнему читают двумя разными способами. На IPv6-адресе API работает, а workers — нет.
- Предлагаемое исправление: один путь для всех приложений — `new Redis(url, opts)` (BullMQ принимает готовый экземпляр ioredis). Либо убирать квадратные скобки и разбирать query-параметры. Добавить тест на `[::1]`.

### [P3] В демо устаревшие числа векторов
- Где: `docs/demo/M0.md:45-47` — «71 вектор», «(144 теста)».
- Доказательство: в 7 наборах 3276 векторов (10 + 14 + 3×1000 + 192 + 60). Фактически прошло: в TS 3298 тестов, в Swift `"Вектор" with 3276 test cases passed`, в Kotlin `tests="3282" failures="0"`.
- Почему это проблема: по демо принимают веху. Расхождение с фактом подрывает доверие к остальным шагам демо.
- Предлагаемое исправление: обновить числа или писать «все наборы каталога» без конкретного числа.
