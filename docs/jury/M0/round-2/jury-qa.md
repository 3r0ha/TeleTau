### [P1] `pnpm test`, `verify.sh` и CI красные на целевой Node 24: `node --test` с каталогом
- Где: `packages/contracts/package.json:22` — `"test": "node --test test/"`; `package.json:13` — `"test": "turbo run test && node --test scripts/test/"`.
- Доказательство: чистая копия по `.gitignore`, `PATH=/opt/homebrew/opt/node@24/bin:$PATH bash scripts/verify.sh`:
  ```
  @teletau/contracts:test: Error: Cannot find module '.../packages/contracts/test'   code: 'MODULE_NOT_FOUND'
  @teletau/contracts:test: Node.js v24.22.2
  ✘ Тесты TS (векторы bashkir-text, контраст токенов, приложения, скрипты)
  EXIT=1
  ```
  Напрямую: на v24.22.2 `node --test test/` и `node --test scripts/test/` дают `✖ test … 'test failed'`, на v26.13.0 оба проходят. Если запустить `turbo run test --continue` на Node 24, падает только `@teletau/contracts#test`, остальные 13 задач зелёные. Glob-форма на Node 24 работает: `node --test 'test/**/*.test.mjs'` — 3/3, `node --test 'scripts/test/*.test.mjs'` — 7/7.
- Почему это проблема:
  - Не выполняется критерий 2 и условие гейта 5 на той версии Node, которую проект объявил целевой.
  - CI (`ci.yml`: `node-version-file: .nvmrc` → 24, затем `pnpm test`) будет красным с первого запуска.
  - Самопроверку в `STATUS.md` («зелёный на всех платформах») делали только на Node 26.
- Предлагаемое исправление:
  - Заменить аргументы на glob-шаблоны в кавычках.
  - В `verify.sh` предупреждать (или падать), если мажорная версия `node -v` не совпадает с `.nvmrc`.

### [P2] `normalize`/`toComparable`/`fold` квадратичны на цепочках ZWJ/ZWNJ на всех трёх платформах (регрессия от исправления M0-15)
- Где:
  - TS: `packages/bashkir-text/src/normalize.ts:35` (`neighbour`) и `:47` (вызов для каждого ZWJ).
  - Swift: `ios/Packages/TeleTauCore/Sources/BashkirText/BashkirText.swift:45,60`.
  - Kotlin: `android/core/bashkirtext/src/main/kotlin/ru/teletau/core/bashkirtext/BashkirText.kt:44,61`.
- Доказательство (`normalize("‍".repeat(n))`):
  | n | TS (Node 26) | Swift (debug) | Kotlin (JDK 21) |
  |---|---|---|---|
  | 10 000 | 1 186 мс | 9 858 мс | 1 079 мс |
  | 20 000 | 9 235 мс | 41 390 мс | 4 976 мс |
  | 40 000 (120 КБ UTF-8) | 25 975 мс | 154 334 мс | 35 017 мс |

  Для сравнения: 500 000 букв «ә» — 178 мс (TS). Чередование `ZWJ+цифра` на 40 000 — 27 мс, то есть деградирует именно цепочка соединителей. `neighbour()` для каждого ZWJ заново проходит всю цепочку, отсюда O(n²).
- Почему это проблема:
  - Модуль `bashkir-text` будет проверять ответы на сервере (M2) и обрабатывать корпус (M4). Тело в 1 МБ, которое пропускает Fastify, — это около 333 тыс. ZWJ, то есть порядка 30 минут заблокированного event loop (экстраполяция квадрата).
  - На Android вставка такого текста в поле ответа даст ANR.
  - Тест «длинный вход 200 000» на всех платформах состоит только из букв, поэтому этого не ловит.
- Предлагаемое исправление: два линейных прохода с массивами «ближайшая не-соединительная кодовая точка слева/справа — буква?». Во все три порта добавить тест «200 000 ZWJ быстрее 1 с».

### [P3] iOS-снапшот не замечает подмену башкирской буквы; на iOS нет проверки кодовых точек строки букв (остаток M0-13)
- Где: `ios/Packages/TeleTauCore/Tests/DesignSystemTests/StartScreenRenderTests.swift:25` (`snapshotMaxDiffShare = 0.002`, допуск по каналу 8).
- Доказательство: в чистой копии заменил `brandTitle` «Кәрәҙ» → «Кәрәз» и в строке букв «Ҙ ҙ» → «З з». Рендер явно неверный, но `✔ Рендер совпадает с эталоном … passed`. Отличаются 171 пиксель из 1 316 640 (0,013%), а допуск — 2 633 пикселя. Подмену эталона тёмной темой тест ловит (99,886%).
- Почему это проблема: правильные особые буквы — ключевой визуальный риск продукта. На Android та же мутация ловится тремя снапшотами и тестом `glyphLine_usesCorrectBashkirCodePoints`, а на iOS нет ни того, ни другого.
- Предлагаемое исправление: сравнивать по областям (заголовок и строка букв) с порогом ≤ 0,005%. Добавить тест кодовых точек `glyphTestLine` и `brandTitle`, как на Android.

### [P3] `verify.sh` применяет миграции к другой БД, чем интеграционные тесты, если порты заданы в `.env` (остаток M0-10)

### [P3] workers не подключаются к Valkey по IPv6-литералу (остаток M0-06)
- Где: `packages/runtime/src/valkey.ts:26` — `host: url.hostname`.
- Доказательство: `parseValkeyUrl("redis://[::1]:36379")` → `host: "[::1]"` → `getaddrinfo ENOTFOUND [::1]`. API с тем же URL получает `PONG`. Разбор расходится и в экзотике: `?db=3` (API → db 3, workers → db 0) и `valkey://h:1` (API молча подключается к хосту `valkey:6379`).
- Предлагаемое исправление: `hostname.replace(/^\[(.*)\]$/, "$1")`. API пусть использует тот же `parseValkeyUrl`, а не разбор ioredis.
